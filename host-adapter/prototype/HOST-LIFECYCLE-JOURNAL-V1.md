# Host Lifecycle Journal v1 — contract specification

**Status:** implementation specification draft; not production approval.  
**Target:** SillyTavern 1.19.0, pinned source commit 06bde939fb1e9c4c8d8641d810f0a916b5bce127.  
**Branch:** host/st-1.19-lifecycle-completion.  
**Release posture:** review-only; NON_READY / FAIL-CLOSED.

This specification consolidates the eleven findings from the independent reviews of PR #842. It defines the protocol for the Core journal, authenticated SillyTavern server proxy, browser bridge, SQLite persistence and recovery tests. Where the repository does not yet expose a trusted Host authority primitive, implementation must connect to the deployment-owned Host root registry and durable root-inventory authority. A browser assertion, adapter token, or the unrelated mechanic-policy visibility authority is not sufficient.

## 1. Scope and invariants

The journal records lifecycle evidence, not chat content and not canonical world state.

1. No raw message text, prompt, attachment bytes, imported file bytes, or export payload is accepted by the Core lifecycle API or stored in the lifecycle journal.
2. A browser event is never authority. The only ingress is the authenticated same-origin SillyTavern server proxy, binding the request to the signed ST session, authenticated account, installation and stable conversation identity.
3. Every mutation is write-ahead: durable PREPARED before the first host write; COMMITTED only after the exact persisted after-state is read back and verified.
4. An unresolved mutation is never automatically committed or aborted after restart.
5. The Core journal is append-only, hash chained, SQLite-backed, FULL synchronous, and writes event plus head in one transaction under the shared coordinator lock.
6. Event replay is idempotent only for the same canonical event envelope under the same event ID. Reusing an ID with changed content is a hard conflict.
7. One mutation may be pending per conversation (single-writer). Distinct conversations may proceed independently, serialized only at the shared SQLite/coordinator boundary.
8. No readiness is inferred from successful transport, a complete flag, caller-provided coverage, or a valid hash alone.
9. Unsupported or uninstrumented Host operations remain NON_READY. Memory→NPC remains DISABLED.
10. The journal is evidence and recovery metadata. It is not the canonical chat store, an anti-rollback authority by itself, or permission to dispatch model requests.

## 2. Identity and scope

### 2.1 Identifiers

- host_installation_id: stable UUID for one ST data-root installation, generated and persisted by the ST server-side identity store.
- authenticated_account_id: stable deployment-mapped account principal resolved from the signed ST session and matched against the Core deployment registry. A mutable display handle is not the principal.
- host_session_id: server-generated UUID stored in the signed SillyTavern session. It rotates when the authenticated account changes and is required on every lifecycle request. It is not an installation identity.
- conversation_uuid: stable UUID persisted in conversation metadata. Filename, title, group name and locator are not identity.
- conversation_id: composite external identifier host_session_id:host_installation_id:conversation_uuid. Core validates all three components against authenticated server context.
- mutation_id: UUID v4 generated by the server-side Host bridge before PREPARED. Unique within installation + account + session + conversation. UUID randomness also makes cross-installation collision negligible.
- event_id: independent UUID v4 generated once per phase event. Persist it locally before transmission and reuse the exact ID and envelope for every retry.

The browser may request identity resolution but cannot choose or overwrite server account/session identity. Missing, malformed, stale, cross-account or mismatched identities return NON_READY/403 and append nothing.

### 2.2 SQLite scope

Event uniqueness is scoped by (host_installation_id, authenticated_account_id, host_session_id, conversation_uuid, event_id). Mutation uniqueness is scoped by the same tuple plus mutation_id. Pending state and status queries use the full tuple; there is no account-wide pending flag. Session rotation does not erase prior history; it creates a new session scope.

The account/installation hash-chain head may remain account-wide, but every event row carries host_session_id and conversation_uuid. All conversation status and recovery queries are scoped to the complete identity tuple.

## 3. Trusted authorization context

Every accepted lifecycle event is bound to this immutable trusted snapshot:

    {
      "authority_id": "deployment-owned stable authority identifier",
      "generation": 12,
      "snapshot_fingerprint": "<64 lowercase hex SHA-256>"
    }

- authority_id identifies the deployment-owned Host authorization/root authority, not a browser, conversation, or adapter token.
- generation is a positive safe integer, monotonically advanced whenever an authorized installation/account/root binding changes or is revoked. It must not roll back after restart. If durable generation recovery cannot be proven, rotate authority_id so all old contexts become stale.
- snapshot_fingerprint is SHA-256 over canonical JSON of authority ID, generation, adapter ID, installation ID, account principal, root ID, and accepted durable root-inventory authority head (sequence, manifest digest and journal-head digest). Core computes it from deployment-owned state; the browser never supplies trusted authority data.
- The ST proxy resolves signed session identity. Core independently resolves the configured adapter/installation/account/root binding and obtains the trusted inventory head. Both must agree on the session/conversation scope.
- Every event stores all three authority fields. Core rejects events whose context is no longer current.
- If authority changes while a mutation is pending, the conversation becomes NON_READY. Recovery cannot commit under stale authority.

The existing MechanicPolicyAuthority is a field-visibility policy authority, not a Host storage authority. Do not reuse or relabel it. The lifecycle implementation must connect to the deployment-owned Host root registry and durable root-inventory head. If no accepted trusted root head exists, return NON_READY rather than fabricate one.

## 4. Mutation manifest and digest semantics

mutation_digest is SHA-256 of canonical UTF-8 JSON (sorted object keys, no insignificant whitespace) for the immutable intent manifest. It contains protocol version, operation allowlist value, mutation ID and full identity scope, sorted affected artifacts, normalized root-relative paths, stable logical artifact IDs, expected pre-state and expected post-state for every artifact (present/absent plus SHA-256 of persisted bytes), lineage references, and the trusted authorization tuple.

The manifest MUST NOT contain raw bytes, message text, prompt content, absolute paths, secrets, or arbitrary caller metadata. Paths are normalized by the server relative to the authorized data root.

The same mutation_digest is repeated in PREPARED and its terminal event. The bridge computes expected post-state before the first write. For deletion the expected state is absence; for import/restore it hashes source bytes locally without sending or storing those bytes in Core.

COMMITTED and ABORTED additionally require receipt_digest: SHA-256 of a canonical persisted-state receipt containing mutation ID, intent digest, observed pre/post artifact identities and digests, read-back result, operation-specific save evidence and authority snapshot. The receipt is stored in the local append-only Host journal; Core receives only its digest. COMMITTED is accepted only when observed post-state exactly matches the intent manifest. ABORTED is accepted only when no target artifact changed or a separately verified rollback restored the exact pre-state. Otherwise return RECOVERY_REQUIRED / NON_READY.

A digest mismatch is never normalized or retried with changed content under the same mutation ID. It freezes the conversation and requires reconciliation.

## 5. Event envelope and API

Every event is a strict allowlisted JSON object. Unknown fields are rejected.

Required common fields: event_id, event_type, occurred_at, host_installation_id, authenticated_account_id, host_session_id, conversation_uuid, authority_id, generation, snapshot_fingerprint, mutation_id, operation and mutation_digest. Terminal events additionally require receipt_digest. occurred_at is trusted-server RFC 3339 UTC. The bridge persists the exact envelope locally before sending, so retries preserve timestamp and event ID.

Core endpoints:
- POST /v1/host-lifecycle/events — append one validated event.
- GET /v1/host-lifecycle/status — read verified status for the authenticated session/conversation.

Identity and authority values in the body are claims to compare, not authority. Core obtains trusted context from adapter authentication, server-side identity resolution, deployment registry and root-inventory authority.

## 6. State machine and idempotency

Allowed transitions:

    NO_PENDING -- PREPARED(mutation_id) --> PENDING
    PENDING -- COMMITTED(same mutation, intent, verified receipt) --> NO_PENDING
    PENDING -- ABORTED(same mutation, intent, verified no-change/rollback receipt) --> NO_PENDING

Rules:
1. No terminal event without a matching PREPARED.
2. No second PREPARED while one mutation is pending in that conversation.
3. Terminal event must match mutation_id, operation, mutation_digest and authority snapshot from PREPARED.
4. COMMITTED and ABORTED are mutually exclusive. No backward transition, second terminal transition, or PREPARED-to-PREPARED transition.
5. A new logical attempt after ABORTED uses a new mutation_id and new event IDs.
6. Inside one SQLite write transaction, check existing event_id BEFORE checking pending-state transition:
   - same event_id + same canonical envelope returns duplicate with original sequence/hash;
   - same event_id + changed envelope returns HOST_LIFECYCLE_EVENT_ID_CONFLICT;
   - only unseen IDs proceed to state validation.
7. Event lookup, duplicate comparison, state validation, insert and head update occur under one BEGIN IMMEDIATE transaction and shared coordinator lock. Unique constraints are the final race guard.
8. A new event ID cannot impersonate an earlier phase or reopen a terminal mutation.

## 7. Concurrency and durability

V1 is single-writer per conversation, not global single-writer. The bridge serializes mutations within a conversation. Core serializes append transactions with the shared coordinator lock and SQLite BEGIN IMMEDIATE. Different conversations can have independent pending mutations.

SQLite requirements: WAL, synchronous=FULL, foreign keys enabled, bounded busy timeout with fail-closed behavior, append-only event triggers, and event insert plus chain-head update in one transaction. Startup verifies sequence continuity, hash chain, canonical encoding, authority snapshot and state-machine consistency.

Acknowledge only after SQLite COMMIT succeeds. If HTTP response is lost after commit, exact retry returns duplicate. If process crashes before commit, rollback leaves no event and retry appends. If it crashes after commit, retry finds the durable event.

## 8. Crash recovery protocol

A pending mutation is never auto-resolved on startup.

1. On startup, bridge activation and before the next mutation, read Core status and verify the complete journal chain and authority context.
2. If no pending mutation exists, compare local journal head with Core status. Continue only when they agree.
3. If Core reports PENDING, load the exact local PREPARED record and receipt by mutation ID. Missing local evidence is NON_READY.
4. Enumerate the exact affected persisted artifacts. Read bytes from disk and compute presence, normalized path, file identity and SHA-256. Never infer persistence from in-memory arrays or a successful save callback alone.
5. Compare observed artifacts with expected pre/post state:
   - exact post-state plus verified save/read-back receipt: replay exact COMMITTED event;
   - exact pre-state plus proof no target changed: append/replay ABORTED;
   - partial, mixed, unexpected, missing, changed-authority or unreadable state: leave PREPARED unresolved and return RECOVERY_REQUIRED / NON_READY.
6. Recovery never silently rewrites files, deletes evidence, auto-restores a backup or infers user intent. Repair requires a separately authorized operation.

If Core is unavailable, no new mutation executes. A native save already completed may remain on disk, but the conversation stays NON_READY until the exact terminal event is durably replayed.

## 9. getConversationStatus() response

The endpoint returns a strict schema:

    {
      "status": "NO_PENDING_MUTATION | PENDING_MUTATION | RECOVERY_REQUIRED | NON_READY",
      "identity": {
        "host_installation_id": "<uuid>",
        "authenticated_account_id": "<opaque principal>",
        "host_session_id": "<uuid>",
        "conversation_uuid": "<uuid>"
      },
      "authority": {
        "authority_id": "<string>",
        "generation": 12,
        "snapshot_fingerprint": "<sha256>"
      },
      "journal": {
        "integrity": "VALID | INVALID",
        "sequence": 42,
        "head_sha256": "<sha256>"
      },
      "pending": null,
      "reason": null
    }

For PENDING_MUTATION, pending contains mutation ID, operation, intent digest, PREPARED event ID and timestamp only. RECOVERY_REQUIRED and NON_READY return stable machine reason codes, never raw paths or chat text. Invalid chain, duplicate pending state, authority/session mismatch, or inconsistent local/Core heads yields NON_READY. Status is read-only; it never resolves a mutation.

## 10. Operation allowlist and SillyTavern 1.19.0 mapping

| Operation | Pinned Host path/hook | Persisted artifact set | V1 disposition |
|---|---|---|---|
| create-message | saveReply() create/append | target chat JSONL + version identity receipt | supported only after disk read-back |
| create-swipe | saveReply() swipe append | chat JSONL + lineage + active swipe metadata | supported only after disk read-back |
| message-edit | messageEditDone() | chat JSONL + old/new version ancestry | supported only after disk read-back |
| select-swipe | endSwipe() | chat JSONL active swipe/index metadata | supported only after disk read-back |
| delete-swipe | deleteSwipe() | chat JSONL + deleted version tombstone | supported only after disk read-back |
| delete-message | deleteMessage(), deleteLastMessage() | chat JSONL + deleted message/version tombstones | supported only after disk read-back |
| delete-chat / delete-group-chat / delete-character-chat-recursive | delChat(), deleteCharacterChatByName(), group/recursive delete routes | every affected chat file and metadata | UNSUPPORTED until multi-artifact receipt exists |
| import / import-character-chat / import-group-chat | destination file, lineage map, group metadata | UNSUPPORTED until source/destination receipts exist |
| export | export/download route | immutable export snapshot and destination receipt | UNSUPPORTED; download-only response is not a mutation |
| restore / backup-restore | backup restore routes | full restored artifact set plus prior-state manifest | UNSUPPORTED until restore isolation/rollback proof |
| copy-branch | copy/duplicate routes | source and destination artifacts plus identity remapping | UNSUPPORTED until both sides are receipted |
| create-branch | createBranch() | parent metadata and new branch chat file | UNSUPPORTED until paired artifact atomicity |
| group-metadata-migration | migrateGroupChatsMetadataFormat() | every rewritten group/chat JSON artifact | UNSUPPORTED until batch snapshot/receipt |

The Core/proxy v1 mutation allowlist currently accepts only create-message, message-send, message-receive, create-swipe, select-swipe, delete-swipe, delete-message, edit-message and rename-chat. The other table rows document known Host paths but are explicitly rejected as unsupported; they are not accepted lifecycle operations. Rename remains candidate-only until its persisted rename/locator behavior is covered by a real file test.

A hook is not proof of persistence. Every supported operation requires PREPARED before first write, exact save completion, fresh disk read-back, artifact-set and digest match, durable local receipt, then Core COMMITTED. Any missing hook or artifact keeps the conversation NON_READY. Export must not fabricate a COMMITTED mutation for a download-only response.

## 11. Failure codes

Minimum stable reason codes:
- HOST_LIFECYCLE_IDENTITY_NOT_AUTHORIZED
- HOST_SESSION_SCOPE_REQUIRED
- HOST_LIFECYCLE_AUTHORITY_STALE
- HOST_LIFECYCLE_EVENT_ID_CONFLICT
- HOST_LIFECYCLE_MUTATION_ALREADY_PENDING
- HOST_LIFECYCLE_MUTATION_PREPARE_MISSING
- HOST_LIFECYCLE_MUTATION_TERMINAL_CONFLICT
- HOST_LIFECYCLE_INTENT_DIGEST_MISMATCH
- HOST_LIFECYCLE_RECEIPT_MISMATCH
- HOST_LIFECYCLE_JOURNAL_INTEGRITY_FAILED
- HOST_LIFECYCLE_RECOVERY_REQUIRED
- HOST_LIFECYCLE_BUSY
- HOST_LIFECYCLE_UNSUPPORTED_OPERATION

No failure path may downgrade to success, infer a terminal event, or expose raw chat content.

## 12. Acceptance tests

Implementation is incomplete until these tests pass on the exact PR HEAD:

1. ID generation, uniqueness scope, invalid IDs, session rotation, cross-session and cross-account rejection.
2. PREPARED→COMMITTED and PREPARED→ABORTED; reject terminal without prepare, duplicate prepare, conflicting terminal and backward transitions.
3. Same event ID/same content returns duplicate even when another mutation is pending; same ID/changed content conflicts; new ID with illegal transition fails.
4. Concurrent appends in one conversation yield exactly one pending PREPARED; different conversations do not share pending state.
5. Event insert/head update are atomic under injected failure; crash-before-commit leaves no event; crash-after-commit and lost response retries as duplicate.
6. Restart recovery for exact pre-state, exact post-state, partial write, changed bytes, missing/unreadable artifact, corrupted receipt, unavailable Core and stale authority.
7. Authority ID/generation/fingerprint are deployment-derived; rotation invalidates stale events/pending recovery; restart cannot roll generation backward.
8. Manifest canonicalization is deterministic and excludes all content bytes/text; changing artifact identity/path/pre/post digest changes intent digest.
9. getConversationStatus() schema, integrity, pending details, reason codes and read-only behavior.
10. Every supported ST 1.19.0 hook has pinned-source and real persisted-file tests. Unsupported operations remain fail-closed.
11. Real create/edit/swipe-select/swipe-delete/message-delete tests verify disk bytes after process restart.
12. Full Runtime, Host Adapter source audit, pinned patch check/validation, browser IndexedDB restart, Windows VSS/reparse tests and Linux filesystem security checks pass on the same exact HEAD.
