# SQLite VFS identity probe — NOT a production security implementation

This probe is a bounded feasibility implementation for Issue #770. It keeps the Node.js node:sqlite API and inserts a native VFS/syscall boundary underneath it. It is not approved for production database opens.

## Exact runtime tested

- Node.js 22.13.0
- Bundled SQLite 3.47.2
- Windows x64 and Linux x64
- Original Windows/Linux open-boundary probe: `56ebf8c6246358be363a83ccc6653fd8828523dc`
- POSIX directory-anchor spike with root-relative component walk and symlink rejection test: `6b0b854fe4659c8e43d6ac5b78bedd0043b395bc`
- Windows relative-open primitives are exercised by `windows_relative_open_test.c`: the test acquires a directory HANDLE chain, opens a child through `NtCreateFile` + `OBJECT_ATTRIBUTES.RootDirectory`, records the full `FILE_ID_INFO`, and attempts to rename the parent while the trusted child HANDLE remains open. If rename succeeds it creates a decoy at the old path; if the OS denies rename, the test requires a fail-closed denial. In both cases the anchored open must still read the trusted object. It also rejects directory and child reparse-point substitutions.
- The helper requests `SYNCHRONIZE` whenever it uses `FILE_SYNCHRONOUS_IO_NONALERT`, and directory handles request `FILE_TRAVERSE`.
- The current Windows VFS test exercises the registered Node `node:sqlite` VFS. It accepts either successful parent rename followed by decoy isolation, or an OS-denied rename while the trusted DB HANDLE remains open (a fail-closed outcome). The standalone relative-open test separately exercises `NtCreateFile` against a renamed parent. Exact-head CI for the latest integration changes is still pending.

## What this probe now demonstrates

1. A temporary in-memory DatabaseSync connection can load the extension.
2. The extension registers a process-default VFS through the SQLite API table supplied by Node.
3. SQLITE_OK_LOAD_PERMANENTLY keeps the extension loaded after the bootstrap connection closes.
4. Ordinary file-backed DatabaseSync connections use that registered VFS.
5. Every file-backed main database must be explicitly registered with a role before SQLite opens it. An unregistered file-backed main database fails closed; in-memory databases are exempt.
6. Role registration performs a native OS open, rejects final-component symlink/reparse-point opens, captures the actual file identity, and pins the native descriptor/HANDLE for the process lifetime.
7. Registering the same physical file identity under two different database roles fails closed.
8. Each later main-database open is checked against the identity captured at role registration. A path replaced after registration but before SQLite's first open is rejected.
9. Main-database replacement races are tested on both platforms. The Linux test injects a hardlink replacement after the VFS stat result and before SQLite can reuse or open the file; Windows tests the CreateFileW boundary. The returned OS object is compared with the pinned identity.
10. WAL, rollback-journal and SHM opens are recognized as sidecars and checked against every registered main-database role.
11. Hardlink replacement races are tested independently for WAL, rollback journal and SHM. Each sidecar must reject an alias to a registered main database. Cross-role sidecar hardlinks and retired sidecar identities are tested on both platforms; rejecting an alias must not truncate the live owner's journal.
12. The process-default VFS and role registry are visible to Node worker threads. Two workers concurrently register/open distinct roles.
13. Linux exercises SQLite's pending-descriptor reuse path and accepts reuse only when the wrapped stat identity matches the registered role.
14. The VFS refuses replacement of its protected open/CreateFileW and Unix stat hooks through the registered VFS xSetSystemCall interface.\n15. File-backed temporary DBs, temporary journals, subjournals, super-journals and transient DB files are rejected until a separately pinned temporary namespace is implemented; pure in-memory databases remain supported.\n16. Unregistered file classes and unregistered xAccess/xDelete paths fail closed instead of delegating to the parent VFS by pathname.\n17. On Windows, both `CreateFileW` and `DeleteFileW` system-call hooks are pinned. The DeleteFileW hook covers SQLite 3.47.2's internal `winShmPurge() → winDelete()` path that bypasses the VFS `xDelete` callback.\n18. On POSIX, the `unlink` system-call hook covers SQLite 3.47.2's internal `unixShmUnmap() → osUnlink()` path that also bypasses the VFS `xDelete` callback.\n17. Integration tests exercise cross-process `BEGIN IMMEDIATE` contention and abrupt process termination after uncommitted WAL frames are written, followed by reopen, row-state verification and `integrity_check`.

The probe still delegates SQLite file methods, locking and normal I/O to the parent VFS. On Linux, a role can now be explicitly bound to the POSIX broker with `logic_engine_vfs_probe_bind_broker(role, socketPath)` after local role registration. For a bound role, main-database `xOpen`/stat/access obtains identity-checked descriptors through `OPEN_MAIN`/`ACCESS_ROLE_FILE`; WAL, SHM and rollback-journal opens use manifest-backed `OPEN_OR_CREATE_SIDECAR`; sidecar `xDelete` and the Unix `unlink` path use broker quarantine deletion. On Linux, the broker-bound VFS now wraps each main DB and rollback-journal file in a custom `sqlite3_file` object. `xRead`, `xWrite`, `xTruncate`, `xSync` and `xFileSize` operate directly on the exact broker-returned descriptor already opened by the parent VFS (`pread`/`pwrite`/`ftruncate`/`fdatasync`/`fsync`/`fstat`); integration tests assert that this direct descriptor-I/O path is exercised. The embedded parent-VFS file shares that same descriptor and remains responsible for SQLite platform locking, `xFileControl`, mmap fetch/unfetch and shared-memory mapping/locking/barriers. Main database, rollback-journal and WAL `xRead`/`xWrite`/`xTruncate`/`xSync`/`xFileSize` operations use the broker-returned descriptor directly; WAL open requires `SQLITE_OPEN_WAL` to enter the broker descriptor path. SHM creation/open is routed through the broker syscall hook, then the parent VFS maps the broker-opened file and implements SQLite's SHM lock/barrier protocol. The integration test now asserts broker-mediated SHM open, successful `xShmMap` calls and `xShmLock` calls without unexpected errors (normal `SQLITE_BUSY` contention is allowed), and reader snapshot isolation while a concurrent writer commits. This validates the hybrid path's exercised behavior; it does not make the SHM mapping or locking implementation independent of the parent VFS. For broker-managed sidecars, the persistent broker manifest is authoritative for inode identity; the process-local sidecar identity registry is retained only for non-broker paths, avoiding false rejection when the filesystem reuses an inode after a broker-confirmed delete. This is an incremental hybrid backend: it removes parent-VFS pathname I/O for the main/WAL/journal byte operations but does not yet implement independent locking or SHM semantics, and is not production approval. This is an opt-in Linux integration proof, not a custom `sqlite3_file` backend or production approval. It now fails closed for file-backed temporary DB/journal, subjournal, super-journal and transient-DB open classes rather than allowing those names to fall through to the unanchored parent VFS. This is a compatibility restriction, not a completed secure temporary-file implementation. On POSIX, file-backed main-DB names are resolved through the parent VFS full-path callback before the parent VFS opens them; WAL/journal xOpen names must match the exact enrolled full path, and registered DB/sidecar opens plus stat/access checks are routed relative to the pinned final parent-directory descriptor. An alias that does not map to the enrolled role fails closed instead of reaching an unanchored sidecar open. `xDelete` checks the enrolled main DB or recorded sidecar identity before unlinking, but the final `fstatat`→`unlinkat` sequence is not atomic against a same-UID/privileged writer. The production closure contract now requires a separate namespace broker that exclusively owns the protected directory and mediates every create/open/rename/delete/sidecar/recovery namespace operation; a delete-only broker or a rename-to-quarantine sequence is not accepted as proof. Protected opens defer `O_TRUNC` until after the opened descriptor passes identity and sidecar-ownership checks, then call `ftruncate` on that same descriptor. Role enrollment rejects a parent directory unless it is owned by the effective UID and has no group/other write bits; `xDelete` rechecks that policy and the enrolled main-DB or process-local sidecar identity immediately before `unlinkat`. This blocks different-UID replacement under the accepted directory-permission policy and rejects static hardlink substitutions. It does not eliminate the same-UID/privileged TOCTOU between the final identity check and `unlinkat`, directory-owner policy changes racing with deletion, or a substituted directory tree enrolled before a persistent trust manifest is checked. Therefore it is a constrained permission-based mitigation, not identity-bound deletion or production approval. A protected same-filesystem quarantine protocol is not accepted as a complete fix while an attacker can mutate the directory during the rename. The production direction is a dedicated namespace broker that exclusively owns the protected directory and mediates every create/open/rename/delete/sidecar/recovery namespace operation. See `docs/security/posix-sqlite-namespace-broker-v1.md` for the implementation contract. This broker is not implemented by this probe. POSIX now also records process-local sidecar identities by database role and kind (WAL/SHM/journal), rejects cross-role and cross-kind aliases, and retains a retired identity when a deleted sidecar still has another hardlink. Windows uses the same retired-identity rule based on the handle's link count. Both registries are bounded and process-local; they have no persistent ownership ledger, per-open reference count, or restart reconciliation, and POSIX still relies on the owner-only parent-directory permission policy described above.

On Windows, the VFS uses the retained parent HANDLE in its `CreateFileW` interception for registered main DB and recognized sidecar opens, so the handle returned to the parent VFS is the anchored handle. Windows `xAccess` is directory-relative and validates the enrolled identity for the main DB; for sidecars it is observational only and does not enroll ownership. Sidecar ownership is claimed only after the actual `xOpen` handle is identity-checked. Windows `xDelete` opens the exact child relative to the anchor, validates the enrolled main-DB or process-local sidecar identity, and marks that opened object for deletion by handle. The actual VFS and standalone helper share one Win32 flag mapper; `CREATE_ALWAYS`, `TRUNCATE_EXISTING`, and `FILE_FLAG_DELETE_ON_CLOSE` are rejected for protected paths because they could mutate/delete an unvalidated object during open. Sidecar identities are checked against enrolled main DBs and other tracked sidecars, but the registry is not persistent across process restarts. The standalone `windows_relative_open.h` tests cover parent rename/decoy isolation, full `FILE_ID_INFO` comparison, directory/child reparse-point rejection, and Win32-shaped relative open/access/delete primitives. The Win32 adapter rejects unmapped flags, overlapped and directory modes, template handles, and unsupported dispositions rather than falling back to a pathname. It also rejects `CREATE_ALWAYS`, `TRUNCATE_EXISTING`, and `FILE_FLAG_DELETE_ON_CLOSE`: NT destructive dispositions can truncate or delete a substituted child before the post-open identity check, so protected opens currently permit only non-destructive create/open dispositions. The Linux broker-client and VFS integration compiles and its first exact-head workflow passed; the latest sidecar delete/recreate regression run is still pending. This remains a constrained integration probe, not a production secure VFS. Windows continues to use its separate handle-relative path and is not connected to the POSIX broker.

## What remains unproven

- **Parent-directory anchoring:** the POSIX spike pins the final parent directory descriptor and uses openat/fstatat/faccessat/unlinkat for registered database and sidecar paths. It passes a test that renames the parent directory, places a decoy at the original path, and verifies that the DB plus WAL/SHM stay in the moved directory. The component walk prevents symlink traversal and pins each directory already opened during acquisition. It does not authenticate the expected identity of each directory component against a separately protected manifest; an attacker who can replace a component before trusted registration may still cause the wrong directory tree to be enrolled. On Windows, the RootDirectory-relative helper is now used by the VFS `CreateFileW` interception and by `xAccess`/`xDelete`. The VFS-level test accepts either anchored operation after a successful parent rename or fail-closed OS denial while the trusted DB HANDLE remains open. Exact-head CI is still required.
- **Pre-registration trust:** role registration is the identity acquisition boundary. If an attacker can redirect the parent path before trusted registration runs, the registration may capture the wrong object. There is no persisted trusted identity ledger across process restarts.
- **Sidecar-to-sidecar collisions:** Both Windows and POSIX maintain process-local WAL/SHM/journal identity registries and reject aliases across roles and sidecar kinds. Regressions cover a live cross-role rollback-journal hardlink and an alias that survives deletion of the original journal pathname. POSIX also tests that xDelete rechecks parent permissions after enrollment. Retired identities are retained while hardlinks survive; stale retired entries consume bounded registry capacity and fail closed on exhaustion. Neither registry is persistent, and per-open reference counting plus crash/restart reconciliation remain unimplemented.
- **Sidecar lifecycle:** the broker now persists `creating → active → deleting → retired` sidecar transitions, supports idempotent delete after retirement, and exposes open-or-create/access operations. The C VFS routes Linux sidecar opens and deletes through those operations when a role is explicitly broker-bound. Full process-restart reconciliation, quarantine operator recovery, per-open reference counting, and Windows parity remain incomplete.
- **Complete VFS operation surface:** On Linux, broker-bound POSIX xOpen/stat/xAccess and sidecar xDelete/unlink now consume broker-verified descriptors and durable manifest operations. The parent VFS still supplies the SQLite file-method table, locking, WAL and SHM implementation. The current end-to-end VFS test uses a same-UID fake broker; the Python daemon's persistent manifest path is tested separately. The bind API still requires local role enrollment and a socket accessible to the application process, so the dedicated-service-UID deployment boundary is not yet integrated. Main-database deletion fails closed when broker-bound. POSIX xOpen/syscall open, stat and xAccess for unbound registered DB/sidecar names remain directory-relative. POSIX role enrollment and xDelete now enforce an owner-only parent-directory permission policy (effective-UID ownership; no group/other write bits), which blocks replacement by a different UID under that policy. This is not identity-bound deletion and does not protect against same-UID/privileged attackers; a protected quarantine/equivalent remains required if those actors are in scope. Temporary-file opens now fail closed for the known file-backed temporary classes; a pinned temporary namespace is not implemented. Cross-process lock contention and an uncommitted-WAL crash/reopen path are now characterized through the parent VFS. Windows and Linux tests exercise WAL-to-DELETE transition and verify that internal SHM deletion passes through the handle-relative DeleteFileW or identity-checked unlink hook. The POSIX unlink still relies on the owner-only directory boundary; it is not atomic against a same-UID directory writer. All other VFS callbacks, parent-VFS bypasses, locking and file-control operations have not been exhaustively reviewed. Windows xAccess is directory-relative and observational for sidecars (it does not mutate the ownership registry); actual sidecar ownership is claimed at the identity-checked xOpen boundary. Windows xDelete validates the enrolled main-DB identity or the matching process-local sidecar identity before deleting the exact opened object.
- **Role inventory:** the test registry is fixed at 32 entries. Production must supply a complete trusted inventory for every persistent database role and fail closed on omissions.
- **Filesystem policy:** ownership, ACLs, permissions, mount boundaries, network filesystems and all filesystem-specific behaviors have not been exhaustively validated.
- **Production lifecycle:** startup ordering, migration, backup/restore, corruption recovery and shutdown/restart behavior remain unimplemented.
- **Other SQLite engines:** this probe targets the SQLite engine embedded in Node's node:sqlite. The uploaded ST-VectorService source uses better-sqlite3 13.0.3 and opens vectors.sqlite in WAL mode. That is a separate SQLite engine and is not covered by this node:sqlite registration proof. It needs its own exact-engine registration/identity test or a deliberate driver integration decision.
- **Host inventory:** this probe does not prove that SillyTavern or every extension has been inventoried, nor that all database opens in the installed Host pass through this VFS.

## Decision from the spike

The native VFS/syscall-wrapper route works inside the exact SQLite engine used by Node 22.13.0 on Windows and Linux. A separate native database binding is not required merely to preserve the existing node:sqlite API.

That is a feasibility decision, not a production security approval. Issue #770 remains open. Do not wire production Core, Coordinator, Provider, Host-ledger, dispatch-ledger or accepted-head files to this probe.

## Remaining implementation gates

1. Add a protected expected-identity manifest for the POSIX directory chain; decide and implement the production deletion primitive (protected same-filesystem quarantine/equivalent, or an explicitly accepted and reviewed owner-only directory threat model); independently test the Windows VFS integration, including sidecar ownership/deletion, role-registration trust, main/sidecar opens, xAccess and xDelete, and VFS-level parent-rename/reparse-point attacks.
2. Extend the directory-relative policy to every required VFS operation, temporary files, and all DB/sidecar lifecycle paths.
3. Define the persisted trusted identity/role ledger and startup reconciliation policy.
4. Extend both process-local sidecar identity registries into a protected persistent ownership lifecycle, including per-open reference counting and WAL/SHM/journal crash/restart reconciliation.
5. Complete production broker-first role enrollment and a cross-UID socket permission/group policy; the current VFS binding requires local role enrollment and the test socket is same-UID only.\n6. Prove exclusive ownership of the required syscall hooks against all supported native components.
7. Inventory every production database role, including Memory Provider, dispatch gateway ledger, accepted-head authority, and direct Core/Provider opens.
8. Evaluate the separate better-sqlite3 engine used by ST-VectorService.
9. Test crash recovery, migrations, backup/restore, shutdown and restart on Windows and Linux.
10. Obtain independent Security review before closing Issue #770 or enabling production opens.

A passing probe test is not a substitute for the remaining gates.
