# Независимая проверка контракта позиции для Spatial/Temporal World Model

**Дата:** 2026-10-28  
**Статус документа:** проект для Core / TimeEngine review; не утверждённый runtime-контракт  
**Основание:** Core decision в [Issue #351, комментарий 6454341242](https://github.com/necromorphic/Logic-Engine/issues/351#issuecomment-6454341242), решение о направлении World Pack typed spatial attributes в [Issue #351, комментарий 6455368293](https://github.com/necromorphic/Logic-Engine/issues/351#issuecomment-6455368293), а также контрактные предложения PR [#548](https://github.com/necromorphic/Logic-Engine/pull/548) и [#551](https://github.com/necromorphic/Logic-Engine/pull/551).

## 1. Вердикт независимой проверки

**Вердикт: BLOCKED — документ пригоден для предметного review, но не доказывает готовность интеграции.**

Core разрешил только изолированную, in-memory, read-only feasibility-проверку существующей границы чтения. Направление «World Pack typed spatial attributes, проверяемые Core на canonical commit boundary» разрешено как следующий этап проектирования. Это **не** разрешение на реализацию, изменение runtime/API/schema/events/adapters/storage или передачу данных Host/Memory/NPC.

Позиция может считаться подтверждённым пространственным фактом только при одновременном выполнении всех условий:
1. значение пришло из явно типизированного поля, а не из произвольного `attributes_json`, текста, `event_type` или догадки модели;
2. World Pack и схема имеют проверяемую неизменяемую идентичность;
3. Core доказал, что схема была разрешена и значение прошло проверку на канонической границе commit;
4. сущность и её идентичность в данном мире непрерывны и не уничтожены;
5. позиция связана с конкретным подтверждённым состоянием Core и однозначной временной границей TimeEngine;
6. снимок и история событий согласованы по composite marker; данные не stale;
7. нет неразрешённого конфликта или неоднозначности.

Если хотя бы одно условие не доказано, пространственный результат не повышается до факта: он возвращается как `UNKNOWN`, `CONFLICT`, `STALE` либо `ABSENT` согласно разделу 4.

## 2. Классы утверждений и доказательств

В документе используются следующие обозначения:

- **[CORE-DECISION]** — решение владельца Core, записанное в Issue #351.
- **[SOURCE-REPORTED]** — конкретный путь/символ указан в решении или существующем отчёте, но в рамках этой задачи его актуальный исходник повторно не исполнялся.
- **[DOC-PROPOSAL]** — предлагаемое нормативное правило будущего контракта; не утверждённое runtime-поведение.
- **[UNVERIFIED]** — необходимая гарантия, которую доступные сведения не доказывают.
- **[NOT-RUN]** — тестовый сценарий сформулирован, но в рамках этой проверки не запускался.

Это документальная независимая проверка архитектурной полноты, а не заявление о полном повторном source audit. Текущий локальный ZIP репозитория не совпадает по времени с более поздними PR; поэтому номера строк и локальные тестовые результаты не выдаются за подтверждение текущего GitHub HEAD.

## 3. Предлагаемый типизированный контракт позиции

### 3.1. Семантика координат v1

Следующие пространственные значения уже выбраны как целевая семантика в [решении Issue #351](https://github.com/necromorphic/Logic-Engine/issues/351#issuecomment-6455368293):

- пространство: трёхмерное;
- координаты: (x, y, z);
- система: единая правая система координат относительно мира;
- направление (+Z): вверх;
- единицы: абстрактные логические единицы, не метры и не пиксели;
- начало отсчёта/anchor: начало сущности (entity-origin);
- позиция не означает физический размер, коллизию, видимость, доступность пути или знание NPC.

**Ограничение:** «world-relative» ещё не задаёт числовое положение начала мира и ориентацию осей (+X) и (+Y) в прикладной сцене. Контракт должен требовать единого frame для одного World Pack/world, но конкретную ориентацию (+X/+Y), преобразования локальных пространств и возможность нескольких пространств требуется подтвердить у владельца продукта/Core. До этого нельзя незаметно преобразовывать координаты из другого frame.

### 3.2. Логическая форма записи

Ниже — **псевдоструктура документации**, не JSON Schema, не новая схема репозитория и не утверждение о существующих полях runtime.

```ts
type PositionV1 = {
  worldId: string;                 // обязательная изоляция мира
  entity_id: string;                // канонический ID сущности в этом мире

  coordinates: {
    x: number;
    y: number;
    z: number;
  };

  frame: {
    kind: "world-relative-right-handed";
    frame_id: string;               // стабильный ID системы координат
    positive_z: "up";
    positive_x: string;             // должен быть определён владельцем
    positive_y: string;             // должен быть определён владельцем
    origin: "entity-origin";
  };

  units: "logical-unit";

  schemaIdentity: {
    worldPackId: string;
    worldPackVersion: string;
    entityTypeId: string;
    schemaDigest: string;
    digestAlgorithm: string;
    canonicalizationVersion: string;
  };

  provenance: {
    sourceKind: "committed-event" | "committed-snapshot";
    sourceEventIds: string[];        // [] допустим только для snapshot-origin
    stateId: string;
    worldRevision: number;
    commit_sequence: number;
    game_time_coordinate: unknown;   // точный тип TimeEngine должен подтвердить
    confirmedBoundaryId: string;
  };

  certainty: "CONFIRMED";
};
```

Наличие поля в этом проекте не считается доказательством, что соответствующее значение реально выдаёт Core. Имена `stateId`, `confirmedBoundaryId`, `schemaDigest`, `canonicalizationVersion` здесь обозначают требования к смыслу; точные имена и наличие эквивалентных идентификаторов должны подтвердить владельцы. Нельзя создавать новый API, cursor или event field на основании этого документа.

### 3.3. Обязательные правила полей

| Поле/группа | Нормативное требование проекта | Что ещё требуется доказать |
|---|---|---|
| `worldId` | Всегда входит в ключ; никакого смешения миров | Сверить точное имя/значение с Core world identity |
| `entity_id` | Ссылается на одну непрерывную идентичность сущности внутри мира | Есть ли incarnation/generation token; как доказать непрерывность |
| `x/y/z` | Все три конечные числовые координаты обязательны; частичная тройка не является позицией | Тип чисел, допустимый диапазон, запрет NaN/Infinity и сериализационные правила |
| `frame` | Одна явная world-relative правая система; (+Z) вверх; anchor — entity-origin | Конвенции (+X/+Y), frame ID и правила преобразования |
| `units` | Только `logical-unit` в v1; никаких неявных метров/пикселей | Совместимость разных World Pack и перевод единиц |
| `schemaIdentity` | Связывает значение с точной неизменяемой версией схемы и типа сущности | Реальный resolver, digest/canonicalization и историческое хранение пока не подтверждены |
| `provenance` | Каждый результат указывает на подтверждённый источник и Core cursor | Совместимость state/event reads и точный TimeEngine boundary mapping |
| `certainty` | `CONFIRMED` допустим только после всех проверок | Существующий runtime такого статуса не выдаёт; это требование будущего контракта |

### 3.4. Отдельные понятия

- **Position** — положение entity-origin в frame.
- **Movement** — переход между двумя подтверждёнными позициями с известным порядком; сам по себе не выводится из двух несопоставимых снимков.
- **Orientation** — направление/вращение; требует отдельного типа, порядка осей, единиц углов и правил нормализации.
- **Pose** — конфигурация/положение частей или суставов; не является синонимом позиции.
- **Teleport** — явный переход, если его семантика выражена подтверждёнными типизированными данными. Большая разница координат сама по себе не доказывает телепортацию.
- **Relative relation** — например, «внутри помещения» или «рядом с объектом»; не эквивалентна числовой позиции и не может автоматически конвертироваться в координаты.

В рамках v1 этим документом предлагается типизировать только Position. Movement/orientation/pose не должны считаться поддержанными без отдельных типизированных правил и одобрения.

## 4. Семантика результата: UNKNOWN, CONFLICT, STALE, ABSENT

Это разные состояния, их нельзя сводить к `null` или трактовать как (0,0,0).

| Статус | Значение | Пример | Разрешённое поведение |
|---|---|---|---|
| `UNKNOWN` | Нет достаточного авторитетного доказательства позиции | Сущность есть, но позиционного события/снимка нет; схема неизвестна | Не выводить координаты; запросить новое доказательство или вернуть unknown |
| `CONFLICT` | Есть два или более несовместимых подтверждения, и правило разрешения не установлено | Два значения позиции для одной сущности на одной границе без однозначного порядка | Не выбирать «последнее» по времени игры или порядку массива; сохранить конфликт |
| `STALE` | Результат построен по маркеру, который уже изменился, либо его свежесть не удалось подтвердить | Core revision/commit sequence изменились после чтения | Отбросить результат, повторить чтение или отказать |
| `ABSENT` | Авторитетное состояние явно сообщает, что позиция не задана/удалена | Допустимое явное удаление position при живой сущности | Не наследовать предыдущие координаты; не подменять UNKNOWN, если факт удаления не подтверждён |
| `UNSUPPORTED` | Источник или семантика не поддерживаются контрактом | Значение из generic attributes или неизвестной схемы | Fail closed; не повышать до CONFIRMED |
| `CONFIRMED` | Позиция однозначна, типизирована, committed, свежа и привязана к согласованной границе | Валидированное значение из принятого канонического изменения | Можно использовать только внутри одобренной границы потребителя; не даёт права на Memory/NPC disclosure |

**Приоритет:** `STALE` блокирует использование ранее вычисленного результата независимо от того, был ли он раньше `CONFIRMED`. `CONFLICT` нельзя понижать до `UNKNOWN`, если это уничтожает диагностически важное противоречие. `ABSENT` требует положительного доказательства отсутствия; отсутствие поля в неполном snapshot не доказывает удаления.

## 5. Происхождение, commit cursor и согласованность Core reads

### 5.1. Разрешённая граница чтения

**[CORE-DECISION]** Для ограниченного read-only feasibility spike Core указал существующие внутренние методы:
- `engine.getState(worldId)` — в комментарии Core указан как `src/application/engine.js:487`;
- `engine.getEvents(worldId, false)` — там же указан как `src/application/engine.js:489`;
- `getSnapshot(id,{})` не заменяет полный inventory мира, поскольку является bounded-selection API.

Эта граница разрешена для изолированного эксперимента, но не является публичным spatial API и не разрешает интеграцию в production.

### 5.2. Обязательный протокол согласованности

Предлагаемый протокол должен выполнять:

1. прочитать (S_1 = getState(worldId));
2. прочитать (E = getEvents(worldId, false));
3. прочитать (S_2 = getState(worldId));
4. проверить, что у (S_1) и (S_2) совпадают `world_id`, `world_revision`, `commit_sequence` и `game_time_coordinate`;
5. проверить, что все события в (E) относятся к тому же миру, валидны и имеют строго определённый порядок по `commit_sequence`;
6. проверить, что события/эффекты, использованные для результата, не выходят за подтверждённый commit cursor и не нарушают выбранную границу;
7. непосредственно перед возвратом результата повторно проверить marker; при изменении — не возвращать старый результат как свежий.

Если любой marker отличается, пакет целиком отбрасывается и перестраивается или возвращается отказ. Нельзя «починить» несогласованность, смешав состояние из (S_1), события из другой ревизии и состояние из (S_2).

**Важно:** этот протокол — одобренная граница feasibility-эксперимента, а не доказательство атомарного совместного чтения всех данных при любых гонках. Устойчивость до момента фактического потребления результата, а также restore anti-rollback должны быть отдельно подтверждены.

### 5.3. Роль идентификаторов

Не смешивать:
- `world_revision` — ревизию состояния мира;
- `commit_sequence` — порядок канонических фиксаций;
- `game_time_coordinate` — игровое время;
- event ID — идентичность события;
- state/snapshot ID — идентичность конкретного снимка, если такая есть;
- TimeEngine segment/checkpoint/boundary ID — подтверждённую временную границу, если её выдаёт TimeEngine.

Игровое время не является уникальным порядком: несколько событий могут иметь одинаковый `game_time_coordinate`. Для детерминированного порядка используется подтверждённый `commit_sequence`, но это само по себе не определяет, какой набор событий входит в исторический ответ TimeEngine.

## 6. Удаление позиции, уничтожение сущности и идентичность

### 6.1. Удаление только позиции

**[DOC-PROPOSAL]** Удаление координат не должно автоматически уничтожать сущность. Если сущность остаётся живой, контракт различает:
- явное подтверждённое удаление позиции → `ABSENT`;
- позиция никогда не была известна → `UNKNOWN`;
- отсутствие position-поля в неполном read → недостаточно данных, результат не может быть `ABSENT`.

Если тип сущности требует обязательную позицию, Core должен отклонить commit, который оставляет живую сущность без требуемого поля, если только отдельное утверждённое правило не допускает переходное состояние. Нельзя одновременно объявить позицию обязательной и молча интерпретировать её отсутствие как норму.

### 6.2. Уничтожение сущности

Подтверждённое уничтожение — терминальное состояние идентичности. После него:
- прежняя позиция больше не является текущей позицией живой сущности;
- пространственная проекция не должна «воскрешать» сущность из старого snapshot/event;
- попытка повторно использовать тот же `entity_id` в том же мире должна быть отклонена, если Core не определит и не одобрит отдельную incarnation-модель;
- новый объект не наследует координаты, ориентацию, позу или provenance уничтоженной сущности.

### 6.3. Статус Core tombstone work

PR [#554](https://github.com/necromorphic/Logic-Engine/pull/554) заявляет изменение Core для запрета повторного использования уничтоженного ID при прямом upsert и rebuild, с регрессионными тестами. На момент этого отчёта PR открыт; в описании указано, что focused tests запускались на предоставленном локальном snapshot, а подтверждение CI текущего PR HEAD ещё требуется. Поэтому здесь это **реализация-кандидат, не подтверждённая гарантия main**.

Даже если PR #554 будет принят, он не решает автоматически:
- историческую идентичность схемы World Pack;
- обязательную spatial validation на всех writer paths;
- политику явного удаления только позиции;
- связь incarnation с историческими пространственными результатами.

## 7. Неизменяемая идентичность World Pack schema

### 7.1. Нормативное требование

Для каждого подтверждённого пространственного значения должна быть восстанавливаема **точная версия схемы**, по которой Core проверил значение на момент commit. Минимальная логическая идентичность:
- World Pack ID;
- версия/идентификатор pack;
- ID типа сущности;
- digest канонического содержимого schema;
- версия алгоритма каноникализации и digest;
- историческая связь этой идентичности с конкретным committed effect/state.

Одного имени файла, номера версии, `attributes_schema` как объекта или текущей версии pack недостаточно. Изменённая схема не должна задним числом менять смысл ранее принятого события. При replay/rebuild старые события должны валидироваться по исторически связанной версии схемы, а не молча по последней.

### 7.2. Fail-closed поведение

Если схема:
- отсутствует;
- не разрешается однозначно;
- имеет неизвестный digest/алгоритм;
- изменилась без новой идентичности;
- не соответствует `entity_type` / `type_id`;
- недоступна при replay/rebuild;
- не была доказанно проверена на canonical commit path,

то пространственный результат получает `UNSUPPORTED` или `UNKNOWN`, а commit typed spatial value должен быть отклонён, если Core утвердит typed spatial field как обязательный валидируемый атрибут. Нельзя объявлять значение подтверждённым только потому, что схема декларирует поле.

### 7.3. Текущее доказательное состояние

- **[CORE-DECISION]** Core прямо предупредил, что декларация `attributes_schema`, generic `attributes_json`, `fact.set`, `located_at` и `event_type` не доказывает runtime-enforced typed spatial source.
- **[UNVERIFIED]** Не подтверждены immutable schema digest storage, исторический schema resolver, каноникализация, обязательная проверка на каждом writer path и rebuild по той же schema identity.
- **[BLOCKER]** До подтверждения этих механизмов ни одна позиция, прочитанная из generic attributes, не становится `CONFIRMED`.

## 8. TimeEngine: подтверждённые границы, одинаковое время, rollback и recovery

### 8.1. Поддерживаемый объём v1

До отдельного решения TimeEngine исторические ответы разрешено проектировать только для состояния на подтверждённой временной границе, если одновременно доказана привязка к Core marker. Не обещать произвольную позицию «в середине сегмента» или на произвольный момент времени.

Историческая запись должна логически связывать:
- идентичность подтверждённой границы TimeEngine;
- игровую временную координату этой границы;
- Core `world_revision`;
- Core `commit_sequence`;
- набор committed изменений, включённых в границу.

Это требование не утверждает, что в текущем API уже существует поле `confirmedBoundaryId`.

### 8.2. Одинаковое игровое время

Если несколько событий имеют одинаковое `game_time_coordinate`, нельзя упорядочивать их только по времени или случайному порядку чтения. Для deterministic replay применяется `commit_sequence`, если Core гарантирует его уникальность/монотонность в нужной области. TimeEngine должен подтвердить, какая граница включает события с равным игровым временем и как она связывается с commit sequence.

### 8.3. Rollback, rebuild, restart

- **Rollback:** все производные позиции, основанные на отменённых событиях, инвалидируются. Старый результат не может оставаться доступным под тем же freshness marker.
- **Rebuild:** повторная сборка из канонической истории должна выдавать тот же результат при одинаковых входах и одинаковой schema identity. Ошибка исторической схемы или противоречивое событие должны завершать восстановление fail-closed, а не пропускаться молча.
- **Restart:** in-memory projection после перезапуска восстанавливается из Core; не считать старую RAM-проекцию источником истины.
- **Revision-only change:** изменение `world_revision` при неизменном `commit_sequence` всё равно должно инвалидировать предыдущий результат.
- **Full database restore / anti-rollback:** Core в Issue #351 явно отметил, что restore, воспроизводящий тот же composite marker, этим протоколом не обнаруживается. Это остаётся отдельным blocker; нельзя заявлять anti-rollback гарантию.

## 9. Вопросы для Core

Эти вопросы должны получить ответ владельца Core до заключения о реализуемости. Предлагаемый ответ в контракте не подменяет решение владельца.

1. **Canonical validation boundary:** какой точный commit path гарантирует, что World Pack schema resolved, digest проверен и typed position валидирована до canonical commit? Перечислить все пути: обычный commit, segment commit, replay/rebuild, rollback, migration, альтернативные writer paths.
2. **Schema identity:** где хранится историческая идентичность схемы и как её можно восстановить после изменения pack, удаления файла или restart? Какой canonicalization/digest algorithm считается авторитетным?
3. **Entity identity:** есть ли incarnation/generation identity кроме `worldId + entity_id`? Если нет, подтверждает ли Core запрет повторного использования tombstoned ID в том же мире для всех путей и историй?
4. **Position removal:** как различить явное удаление позиции, отсутствие поля из-за частичного snapshot и неизвестную позицию? Как вести себя, если schema объявляет поле обязательным?
5. **Source provenance:** какие реальные поля дают state ID, event IDs, `world_revision`, `commit_sequence` и game-time coordinate? Какие из них durable и immutable?
6. **Read consistency:** подтверждает ли Core bracketed `getState → getEvents → getState` protocol достаточную согласованность для этой read-only проекции? Какова точная точка freshness re-check перед возвратом?
7. **Commit ordering:** гарантирован ли строгий порядок `commit_sequence` и его уникальность в одном мире? Как обрабатываются gaps/duplicates и invalid events?
8. **Rollback/rebuild:** какой проверенный invariant гарантирует invalidation readers и полное удаление производных эффектов от отменённых событий?
9. **Atomicity:** preflight rebuild предотвращает разрушение текущей проекции при ошибочной истории или только обнаруживает ошибку до/после определённого шага? Нужна ссылка на тест/транзакционную гарантию.
10. **Compatibility:** как legacy World Packs/entities без typed spatial fields продолжают работать без случайного превращения отсутствующей позиции в ошибку или в подтверждённую позицию?
11. **Writer-path audit:** какой список путей изменения сущностей считается полным и каким тестом доказано, что обход validation boundary невозможен?
12. **Status vocabulary:** согласует ли Core `UNKNOWN`, `CONFLICT`, `STALE`, `ABSENT`, `UNSUPPORTED` как разные read outcomes, а `REJECTED` — как write/commit outcome?

### 11.1. Команды и тестовые доказательства

Команды для фактического запуска пока не фиксируются как универсальные: владельцы должны сначала подтвердить точный HEAD, тестовые entry points и допустимую изолированную ветку. Перед запуском в отчёте необходимо записать:
- точный commit SHA и branch;
- точные команды;
- exit code и полный результат тестов;
- ссылки на CI runs, привязанные к тому же SHA;
- какие тесты новые, какие существующие;
- что тест подтверждает и чего не подтверждает.

Наличие существующего успешного CI на другом SHA не засчитывается как PASS текущего контракта. Ни один POS-сценарий не объявляется пройденным в этом документе.

## 13. Блокеры интеграции

1. **Typed-source enforcement:** нет доказательства, что spatial поля реально валидируются на всех canonical writer/commit paths.
2. **Immutable schema identity:** нет подтверждённой схемы digest/canonicalization и исторического восстановления исходной схемы.
3. **Entity incarnation:** политика tombstone/ID reuse требует подтверждения на текущем main и всех путях.
4. **Core–TimeEngine mapping:** нет доказанного точного соответствия confirmed boundary ↔ Core marker/commit_sequence.
5. **Freshness and atomicity:** bracketed read разрешён для bounded experiment, но гарантии stale readers, rollback/rebuild atomicity и race до consumption требуют тестов/подтверждения.
6. **Position removal semantics:** требуется решение о явном удалении поля и поведении обязательных полей.
7. **Coordinate completeness:** (+Z), frame, units и entity-origin заданы; конвенции (+X/+Y), frame identity и преобразования не полностью определены.
8. **Test evidence:** POS test matrix не запускалась в рамках этой проверки; CI по точному head документа ещё должен быть проверен после создания PR.
9. **Consumer boundary:** spatial result не является разрешением для Host/Memory/NPC; Memory→NPC остаётся независимо заблокирован.
