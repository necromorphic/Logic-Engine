# Core 1.7 — отчёт для начала разработки временного блока

**Статус:** архитектурная постановка и план первого исполняемого среза; runtime временного блока ещё не реализован этим документом.  
**Ветка подготовки:** `docs/core-1.7-time-block-start`  
**Основа:** текущие контракты Core на `main`, прежде всего `docs/00-architecture-baseline.md`, `docs/02-turn-event-delivery-lifecycle.md`, `docs/03-storage-and-persistence-contract.md`, `docs/04-world-pack-format.md`, `docs/05-causal-rollback-algorithm.md`, `docs/06-npc-autonomy-and-process-manager.md`, `docs/10-open-decisions.md`, `docs/12-stage-roadmap.md`, `docs/18-rollback-and-causality.md`, `docs/25-universal-mechanics-system.md`, `docs/26-mechanics-contracts.md`.

## 1. Резюме для реализации

Временной блок должен стать доменной подсистемой модульного монолита Logic-Engine. Он не является отдельным сервисом, не привязан к SillyTavern и не должен самостоятельно переписывать каноническое состояние. Его ответственность — владеть игровыми временными координатами и правилами продвижения времени, планировать временные триггеры и выдавать упорядоченные предложения/результаты продвижения через существующий канонический pipeline Core.

Первый срез должен быть **маленьким, детерминированным, сохраняемым и проверяемым**:

1. Явное представление текущего игрового времени и календарной политики мира.
2. Авторизованная команда «продвинуть игровое время на интервал»; никаких автоматических тиков от настенных часов ОС.
3. Проверка диапазона, ограничения мира и ожидаемой ревизии; идемпотентный повтор команды.
4. Детерминированная сегментация интервала и порядок обработки временных границ.
5. Устойчивое сохранение результата через текущий Core event/commit pipeline, аудит и механизм ревизий — без параллельной таблицы канонической истины.
6. Проверки повторного запуска, сбоя, повторного запроса, rollback и изоляции миров.

Не начинать с полноценного календарного UI, сложной астрономии, непрерывной физической симуляции, автономного LLM-расписания или интеграции с ST. Сначала требуется доказать корректность временной модели и границ коммита.

## 2. Что уже зафиксировано проектом

Следующие решения уже присутствуют в архитектурных документах и должны считаться исходными ограничениями до отдельного ADR:

- Реальное системное время используется для диагностики/аудита, но **не продвигает игровой мир**.
- Игровое время изменяется только подтверждённой игровой операцией или явным запросом пропустить время.
- Обычное действие по умолчанию не может продвинуть более **12 игровых часов**; явный пропуск ограничен **7 игровыми днями на запрос**. Длинные интервалы сегментируются.
- Продвижение процессов параллельно должно обрабатываться в детерминированном порядке; порядок исполнения не должен сам по себе создавать причинность.
- Временные политики и календарная семантика могут зависеть от мира, но только через валидированную конфигурацию World Pack. Ядро задаёт инварианты и безопасный исполнитель.
- Длительные процессы могут быть непрерывными, дискретными или смешанными. Нельзя требовать, чтобы каждая механика использовала численный тик.
- Неопределённая или неподдерживаемая механика не исполняется по догадке модели: она становится явным результатом unknown/review согласно контракту механик.
- События и эффекты проходят обычную проверку, каноническую запись, причинное связывание и аудит.
- Откат — новая операция над текущим состоянием с сохранением аудита, а не удаление истории. Временные последствия должны иметь достаточно причинных ссылок, чтобы не сохранять эффект, единственная необходимая причина которого отменена.
- Состояние и процессы изолированы по `world_id`. World Pack и версия его временной политики должны быть определяемы для каждой операции и воспроизводимы при аудите.
- Механики мира — настраиваемая инфраструктура. Временной блок не должен вшивать жанровые правила, примерный мир или конкретную игровую механику.

## 3. Что не следует считать реализованным

Документы описывают целевую архитектуру, но сами по себе не доказывают наличие работающего временного runtime. Перед кодированием нужно проверить актуальный `main` и существующие операции хранилища. В текущем базовом контракте ещё не установлены все необходимые для полного временного блока детали:

- законченный API игрового времени и сериализованная операция продвижения интервала;
- авторитетная календарная модель с часовым поясом/эпохой/длительностью суток, если конкретный мир требует такой настройки;
- постоянный планировщик, восстанавливаемый после перезапуска;
- единый контракт для триггеров на границе интервала и процессов, попадающих внутрь интервала;
- окончательная атомарная граница продвижения: целый интервал, сегмент или отдельное событие;
- общая политика конфликта для одновременных временных событий;
- контракт возобновления после частичного сбоя без двойного применения эффектов;
- завершённая временная семантика rollback для процессов и зависимых событий;
- API/контракт для уведомления NPC и повествования о событиях, произошедших вне сцены.

Не добавлять эти возможности неявно и не утверждать, что они существуют, пока код и тесты этого не подтверждают.

## 4. Границы ответственности

| Компонент | Ответственность | Не должен |
|---|---|---|
| Core domain / time | Игровые координаты, временные политики, проверка интервала, детерминированная сегментация | Использовать системные часы как источник игрового прогресса |
| Canonical event pipeline | Проверка, причинные метаданные, атомарная запись подтверждённых эффектов, ревизия и аудит | Принимать произвольное состояние от планировщика напрямую |
| Time scheduler / Process Manager | Находить наступившие временные триггеры и due-процессы; готовить детерминированный набор работы | Самостоятельно коммитить канонические эффекты или выдавать порядок исполнения за причинность |
| World Pack / mechanics | Декларировать календарную политику и временную семантику поддерживаемых механик/процессов | Выполнять произвольный код или переопределять инварианты Core |
| NPC subsystem | Решения NPC, планы, цели, допустимые действия и actor-relative контекст | Считать наступление срока автоматическим доказательством знания NPC или факта доставки |
| Narrative / adapter | Представлять подтверждённые и разрешённые результаты; при необходимости отслеживать доставку | Создавать канонические события из текста или считать событие известным игроку без канала |
| Storage | Сохранять подтверждённое состояние, идемпотентность, аудит и восстановление в существующей границе владения | Создавать вторую независимую каноническую БД времени без архитектурного решения |

## 5. Предлагаемая доменная модель для обсуждения кода

Это проектный контракт для первого среза, а не уже утверждённая схема API или таблиц. Сначала реализовать как типы/чистые функции и покрыть тестами; публичные поля закреплять только после сверки с текущими схемами.

### 5.1 GameTime

Представляет позицию мира на его временной шкале. Минимальный безопасный вариант — целочисленная координата в базовых единицах времени, относительно стабильной эпохи мира. Нельзя использовать float как каноническое значение времени. Выбор единицы (например, секунды/минуты) должен быть единым для ядра и не обязан совпадать с отображением календаря.

### 5.2 TimePolicy

Версионируемая декларативная политика World Pack, которая задаёт допустимые границы и преобразование канонической координаты в календарное представление. Для первого среза следует поддержать только те параметры, которым определены точные семантика и тесты; не вводить универсальную сложную календарную систему без потребности. Политика должна быть закреплена за миром/операцией так, чтобы исторический результат оставался интерпретируемым.

### 5.3 AdvanceTimeRequest

Намерение продвинуть время: `world_id`, величина/целевая координата, тип причины (обычное действие или явный пропуск), ожидаемая ревизия и ключ идемпотентности — с точными именами полей после согласования с существующим API. Не доверять телу запроса как доказательству полномочий: авторизация берётся из доверенной границы адаптера/хоста.

### 5.4 TimeAdvanceResult

Структурированный результат, который отличает принятие интервала, отказ валидации, конфликт устаревшей ревизии, повтор уже обработанного запроса и безопасный отказ планировщика. Ошибка/тайм-аут не равны нулевому прошедшему времени и не должны выдавать ложный успех.

### 5.5 ScheduledTrigger / DueWork

Внутреннее представление того, что становится due на выбранном интервале. Должно иметь устойчивую идентичность/причинное происхождение, чёткую границу включения времени (например, `(from, to]`) и стабильный tie-break. Идентификатор не должен зависеть от случайного порядка обхода массива.

### 5.6 Checkpoint

Чекпоинт нужен только если выбранная граница коммита позволяет прогрессировать частями. Он не должен быть вторым источником истины. Если один интервал коммитится атомарно, не создавать отдельный долговременный checkpoint без необходимости. Если прогресс частичный, контракт обязан объяснить, как повтор и восстановление избегают двойных эффектов.

## 6. Главный нерешённый выбор: атомарность интервала

Перед scheduler runtime принять и проверить решение о транзакционной границе:

**Вариант A — весь интервал атомарен.** Все due-триггеры и эффекты интервала проверяются и коммитятся как одна операция. Простая семантика all-or-nothing, но длинные интервалы и большой объём работы могут быть дорогими; поэтому нужны ограничение длины и сегментация с чётким определением, является ли сегмент самостоятельным коммитом.

**Вариант B — каждый сегмент атомарен.** Интервал разбивается на детерминированные сегменты, каждый сегмент имеет свою ревизию/события/идемпотентность. После сбоя уже подтверждённые сегменты остаются действительными, а повтор продолжает с доказанного checkpoint. Это проще для длинной симуляции, но требует более строгого контракта частичного успеха, причинности, повторного запуска и пользовательского отчёта.

**Вариант C — каждый due event атомарен.** Максимальная гранулярность восстановления, но выше риск промежуточного состояния, зависимого от порядка, и сложнее воспроизводить результат.

**Рекомендация:** не выбирать только по удобству кода. Сначала построить тестовый сценарий с двумя независимыми событиями и одним конфликтом, затем проверить восстановление после сбоя. Для первого среза предпочтительна минимальная атомарная операция, которая укладывается в существующую транзакционную модель Core. Если длинные интервалы сегментируются на несколько коммитов, это должно быть явно видно в контракте, аудите и результате операции.

## 7. Алгоритм первого среза

1. Принять явно запрошенную операцию и определить доверенный адаптер/полномочия.
2. Прочитать текущую позицию времени, политику мира и согласованный снимок на ожидаемой ревизии.
3. Проверить тип продвижения, диапазон, максимальный интервал, границы мира и idempotency key.
4. Построить детерминированный список временных границ и due-работы без мутации канонического состояния.
5. Сгруппировать одновременную работу согласно объявленной политике конфликтов; не разрешать неизвестные конфликты случайным порядком.
6. Рассчитать эффекты через поддерживаемые механики/процессы; неоднозначные решения вынести в явный результат review/adjudication.
7. Повторно проверить актуальность необходимых предусловий и expected revision перед коммитом.
8. Передать подтверждённые эффекты в канонический Core pipeline с причинными ссылками, аудитом и идемпотентностью.
9. Зафиксировать новую временную координату только в той же согласованной границе, что и соответствующая операция продвижения.
10. Вернуть результат с committed revision, фактическим покрытым интервалом, статусом и идентификаторами событий — только если эти данные реально подтверждены коммитом.
11. Если операция прервана, восстановиться по выбранной атомарной семантике. Не считать неизвестный исход коммита отказом и не повторять эффекты вслепую.

Порядок выше — целевая последовательность. Если существующий Core API не поддерживает необходимую транзакционную границу, сначала расширить его контракт и тесты, а не обходить его прямой записью в SQLite.

## 8. Обязательные тесты для первой вертикали

### Время и политика
- игровое время не меняется от задержки/ожидания и изменения системных часов;
- нулевой, отрицательный, некорректный и слишком большой интервал отклоняется предсказуемо;
- обычное действие и явный пропуск применяют разные утверждённые лимиты;
- границы сегментов стабильны и не пропускают/не дублируют due-trigger;
- одна и та же операция на одинаковом снимке даёт одинаковый порядок работы.

### Идемпотентность и конкуренция
- повтор с тем же idempotency key не применяет эффекты повторно;
- одинаковое тело с новым ключом рассматривается согласно контракту как новая операция, а не автоматически как retry;
- два конкурирующих advance-запроса с одной expected revision не могут оба молча перезаписать позицию;
- stale revision, неверный мир или отказ авторизации не изменяют каноническое состояние.

### События и процессы
- событие ровно на конечной границе интервала обрабатывается один раз;
- два независимых due-события не получают искусственную причинную зависимость только из-за порядка обработки;
- конфликт неразрешимой работы создаёт безопасный review/unknown результат, а не случайного победителя;
- событие без доступного подтверждённого источника не становится каноническим только из-за наступления времени;
- отключение механики не стирает последствия и применяет явно определённую политику к уже запущенному процессу.

### Сбой, восстановление и rollback
- отказ до коммита не оставляет частичное каноническое продвижение;
- отказ после подтверждённого коммита и повтор запроса не дублируют эффекты;
- restart во время сегментированного интервала не теряет и не повторяет подтверждённую работу;
- rollback причины корректно пересчитывает зависимые временные эффекты, сохраняя независимые ветви;
- audit append-only, а новая ревизия не маскируется под старую;
- результат повторного восстановления совпадает с результатом чистого выполнения на том же исходном состоянии.

### Мировая изоляция и конфигурация
- время, политика, планировщик и checkpoint одного мира не влияют на другой;
- изменение версии TimePolicy — явная авторская миграция/смена конфигурации, а не молчаливое переписывание истории;
- неизвестный оператор или неподдерживаемая временная механика не исполняется;
- никакие тесты не требуют заполненной библиотеки игровых механик или демонстрационного World Pack.

## 9. Этапы реализации

### T0 — аудит текущих швов
- Проверить актуальные Core commands/effects, snapshot/revision, idempotency, rollback и mechanic-instance runtime.
- Составить таблицу: доступно сейчас / требует внутреннего контракта / требует изменения схемы.
- Зафиксировать точные файлы и тесты; не дублировать уже существующие возможности.

### T1 — чистая доменная вертикаль
- Типы и чистые функции для канонического времени, проверки интервала, сегментации и порядка due-триггеров.
- Unit/property tests для границ, больших интервалов, переполнения, детерминизма и календарной политики.
- Без новых таблиц и API до доказательства необходимости.

### T2 — операция продвижения
- Встроить explicit advance command в существующий application pipeline.
- Использовать существующую авторизацию, revision, idempotency, audit и event commit.
- Интеграционные тесты на реальном SQLite/Core runtime и конкуренцию.

### T3 — минимальный планировщик
- Зарегистрировать внутренние due-work элементы и обработать простые детерминированные временные триггеры.
- Не добавлять LLM-вызовы в критическую транзакцию.
- Проверить restart/replay и атомарность.

### T4 — Process Manager handoff
- Согласовать контракт с NPC/Process Manager: создание, пауза, отмена, блокировки, завершение, просрочка, reportability и rollback.
- Процессы принадлежат своим доменным владельцам; scheduler только инициирует их продвижение.
- Тестировать off-screen progression без ложного знания NPC/игрока.

### T5 — World Pack и собственное приложение
- Оформить только необходимые настройки времени в версионируемом World Pack контракте.
- Оставить API adapter-independent; UI лишь запрашивает операции и отображает подтверждённые результаты.
- Не делать SillyTavern обязательной зависимостью и не менять текущую векторизацию.

## 10. Решения, которые требуют явного ADR или подтверждения владельцев

1. Каноническая единица времени и стабильная эпоха; допустимы ли отрицательные координаты/время до начала мира.
2. Минимальный календарный контракт: только elapsed-time или также calendar date/time, leap rules, локальные часы и временные зоны.
3. Граница включения событий на интервале и семантика триггера на текущей позиции времени.
4. Максимальная длина сегмента и политика длительного advance.
5. Атомарность: весь интервал, сегмент или due event; семантика частичного успеха.
6. Конфликт двух событий на одной временной отметке: какие случаи решаются декларативно, а какие требуют review.
7. Должен ли scheduler быть полностью восстанавливаемым из канонических событий или нужна отдельная производная очередь/checkpoint.
8. Кто и как может запрашивать пропуск времени, а также как это выражается в trusted adapter contract.
9. Как текущая механика версии и её `lifecycle_policy.on_disable` взаимодействует с активными процессами.
10. Какие события и временные результаты требуют нарратива/доставки, а какие остаются только в состоянии мира.

До принятия решения безопасные defaults: никаких автоматических тиков, никакой скрытой мутации, никакой недекларированной календарной магии, никакого ложного полного успеха после частичного коммита.

## 11. Критерии готовности первой вертикали

Первый срез считается принятым только когда:

- операция продвижения реализована через существующий Core application/event path;
- текущее время хранится в каноническом состоянии мира и восстанавливается из persistent storage;
- world isolation, trusted authorization, expected revision и idempotency проверены интеграционно;
- границы интервалов и порядок работы детерминированы;
- ошибки и неизвестные исходы не выглядят как успешное продвижение;
- rollback и restart имеют тестируемую семантику;
- README, контракты и статус реализации соответствуют фактическому коду;
- все новые тесты проходят на точном PR head, а не только на базовой ветке.

## 12. Начальный набор файлов — только после аудита

Ожидаемое направление, не обязательные имена и не приказ создавать все файлы сразу:

- `src/time/` — доменные типы и чистые вычисления, если текущая структура не предоставляет подходящего места;
- `src/application/advance-world-time.js` или существующий аналог — use case;
- отдельный scheduler/process manager только после фиксации его ownership и восстановления;
- тесты рядом с доменной логикой и интеграционные тесты через реальный Core storage/pipeline;
- схема World Pack изменяется только после утверждения минимальных календарных полей и обратной совместимости.

**Запрет на shortcut:** не обновлять игровое время прямой записью в SQLite из адаптера, не запускать бесконечный setInterval/cron как источник времени мира, не смешивать системное время с игровым и не трактовать успешно созданный narration prompt как доказательство коммита.

## Итог

Начать с T0: аудит текущих команд, эффектов, ревизий, идемпотентности и rollback; затем построить чистые временные функции и тесты. После этого — одна явная операция advance, проведённая через канонический pipeline. Планировщик и автономные процессы наращивать только поверх этой вертикали. Это даёт реальную точку старта разработки без преждевременного закрепления спорной схемы хранения или создания параллельного ядра времени.
