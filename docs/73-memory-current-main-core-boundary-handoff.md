## 2. Required boundary contract, fail-closed behavior, and acceptance tests

| Boundary | Owner(s) | Minimum contract decision | Fail-closed behavior | Exact acceptance test required |
|---|---|---|---|---|
| Retrieval completeness | Memory; Core supplies authoritative source/index facts as needed | Define a trusted operation result that distinguishes complete-empty, complete-nonempty, partial, unavailable, timeout, and index-unavailable, without exposing filtered candidate counts. | Do not convert errors, truncation, or unavailable index into complete-empty. | For each outcome, force the backend condition and assert the distinct operation status; also assert a fully filtered result reveals no hidden candidate existence/count. |
| Trusted field authorization | Core owns enforcement and trusted requester/actor binding; Memory supplies record/field semantics; host must configure policy | Approve the production policy and bind requester, world, recipient, purpose, exact target, fields, and snapshot. PR #101's callback is opt-in, not authorization by itself. | Missing policy, unknown field, policy throw, invalid binding, or stale/unverifiable request returns a generic unavailable/denied shape with no protected payload or existence leak. | Against the real API, test policy absent (non-self target denied), explicit host policy allowlists only named fields, policy throws/denies, wrong actor/world/recipient/purpose, mixed allowed+withheld targets, and concurrent policy/source change. |
| Source identity/version and summary lineage | Core owns canonical source identity/version/validity; Memory owns record IDs/versions and derived lineage; joint mapping approval | Specify the mapping from each Memory record version to stable world-scoped canonical source IDs and versions, plus every materially contributing source version for summaries. | Missing/ambiguous source binding cannot be called current; derived summaries inherit the strongest applicable source access restriction and become stale when required lineage is stale. | Create record and summary from source S/v1; correct or replace S with v2; verify old record/summary is not represented as current and a summary with independent valid support retains only that support with lineage intact. |
| Invalidation, retraction, revocation | Core owns canonical validity/rollback/access truth; Memory owns derived-record/index lifecycle | Decide how canonical invalidation and access-policy revocation are surfaced and what is rechecked at read/serialization time. | Until source validity and access can be revalidated, withhold protected current-only results; preserve audit/history rather than silently rewriting history. | Revoke access and retract/invalidate source after indexing; query by exact ID, search hit, snippet, count, summary, and paginated path; assert no disclosure after revocation and stale derived items are marked/recomputed. |
| Rollback/rebuild with unchanged `commit_sequence` | Core owns rollback/source truth and any durable signal; Memory owns recoverable reconciliation | Choose an approved signal/scan contract that detects event additions **and** validity/revision changes, survives restart, and only claims currentness after a complete successful reconciliation. | If inventory is incomplete, a scan fails, or a marker cannot be trusted, do not advance the completed marker or claim currentness; retry safely. | Snapshot world at revision R/sequence C; rollback invalidates a source and advances revision while sequence remains C; stop/restart reconciliation mid-scan; verify detection, idempotent replay, dependent invalidation, and no false current status. |
| Index freshness/health | Memory owns index health and rebuild state; Core owns source validity; joint definition of currentness | Define separate source freshness/reconciliation and index availability/rebuild health dimensions; do not equate `ready` with `current`. | Lagging/unavailable/rebuilding or unknown state cannot be reported as current; strict-current queries fail closed or return explicit stale/partial state. | Inject index outage, lag, rebuild, missing source, and rollback-only revision change; assert status and result contents reflect each independently. |
| Persistence, audit, transaction boundary | Memory owns its record mutations and operation audit; Core owns canonical audit/transaction/rollback; Core + Memory approve coupling | Decide where authoritative Memory records live and whether any write must be atomic with Core state or an external index. No such coupling is implied by `SQLiteStore.tx`. | If atomicity/commit result is unknown, do not report a durable success; do not leave a projection marked current after a failed authoritative write. | Crash/fail between authoritative write, audit, and index update; retry with same idempotency key; assert no duplicate authoritative records, audit completeness, recoverable index rebuild, and accurate status. |

## 3. Source-change/reconciliation options — comparison only

No option is implemented or selected by this document. Do not add an outbox, cursor, schema, store, callback, or API until Core decides.

| Option | Benefit | Cost/risk | Decision owner / minimum evidence |
|---|---|---|---|
| A. Transactional durable outbox/change journal | Precise replayable signal if committed atomically with every relevant canonical mutation, including rollback/retraction. | Requires Core schema/mutation changes, retention/cursor semantics, and a proven atomic write boundary. A non-transactional callback is not equivalent. | Core decides whether this is viable; demonstrate every source mutation and rollback writes a durable record in the same transaction, with restart/replay tests. |
| B. Consume existing canonical event + rollback/validity journal | Reuses existing authoritative source records and avoids a second signal table if those records are queryable completely. | Must define a stable scan cursor across additions and invalidations; event commit sequence alone misses rollback-only validity changes. | Core confirms complete query API/transaction snapshot and cursor semantics; tests cover duplicate/out-of-order records and rollback with unchanged sequence. |
| C. Recoverable revision-triggered full reconciliation | Does not require an outbox if Memory can obtain a complete authoritative source inventory from a consistent snapshot. | Potentially expensive; requires full inventory, stable source identity, and guarantee that every relevant validity change is detectable by revision or periodic comparison. | Core proves inventory completeness and revision semantics; Memory proves idempotent scan, crash recovery, and marker advances only after complete scan. |
| D. Hybrid polling + periodic full comparison | Can reduce routine cost while repairing missed changes. | Incremental signal may still be incomplete; periodic comparison interval bounds detection latency but cannot justify immediate-current claims. | Joint Core/Memory decision; define maximum stale window, strict-current behavior, and tests for missed incremental changes recovered by full comparison. |

**Current evidence:** PR #114 proves that a trusted operational state read can observe a rollback-only revision movement together with commit sequence. It does **not** by itself provide an authorized, complete, durable source inventory/change feed to Memory. A `world_revision`, `commit_sequence`, context manifest, or generic event must not be promoted into a Memory change signal without a contract proving coverage and recovery.

## 4. Cross-block coordination and scope

- **Core:** confirm the authoritative source inventory/read boundary available to Memory; decide source-change option and transaction ownership; define which fields/policies a host may authorize in production; confirm source version/validity semantics.
- **Memory:** own the record/version, retrieval completeness, summary lineage/permission propagation, index health, invalidation lifecycle, and reconciliation policy. Do not edit Core or NPC runtime.
- **NPC / Issue #70:** own candidate-consumer/admission and actor-relative interpretation tests. Memory must not duplicate acquisition, delivery, receipt, or belief logic. Do not close #70 based on this document.
- **Core canonical write/replay / Issue #77:** remains separate; this handoff does not claim its acceptance criteria are met or close it.
- **Host/vectorization integration:** identify and inspect the actual installed extension/API before selecting a Memory adapter or storage design; do not assume it is absent and do not create a parallel vector store.
