**Тип:** локальные PC-тесты и диагностика.  
**Приоритет:** следующий исполняемый этап после завершённых D5.x проверок Issue #258.  
**Статус до начала:** NOT STARTED.  
**Дата постановки:** 2026-10-30.

## 1. Цель

Провести воспроизводимые проверки локальных компонентов на ПК, не меняя production-код и не затрагивая рабочие данные:

1. Отдельный ST-VectorService: запуск в изоляции, API, SQLite/Vectra, авторизация, валидация, embedding proxy и завершение процесса.
2. Диагностический пакет SillyTavern → Logic-Engine Core: только безопасная проверка доступности `/health`.
3. Контроль целостности и изоляции основного и тестового окружений.

Результат — фактический отчёт с командами, логами без секретов, метриками до/после и точным разделением PASS / PARTIAL / FAIL / BLOCKED / NOT TESTED.

## 4. Этап 0 — baseline и безопасность

До тестов:

1. Снять список процессов/PID и портов для ST 8000, ST 8010, Core 8787, Ollama 11434 и VectorService.
2. Зафиксировать версии Node.js/npm, фактические пути, Git HEAD и `git status --short` только для чтения.
3. Проверить, что тестовый каталог VectorService и тестовая БД не существуют либо пусты. Не переиспользовать существующие данные.
4. Изучить `package.json`, `server.js`, `start.bat`, конфигурацию, маршруты и миграции VectorService.
5. Проверить все места чтения секрета: приоритет env/config, наличие literal secret, вывод диагностических полей, поведение при пустом/неверном ключе.
6. Зафиксировать, какие порты и адреса реально настраиваются через env.

**Обязательное правило по секрету:** значение из `start.bat` не копировать в тесты, терминал, Git, Notion или отчёт. В тестовой копии использовать новый случайный ключ из env. Не менять секрет уже работающего экземпляра без отдельного разрешения. Если выяснится, что архивный ключ совпадает с активным ключом рабочего сервиса, немедленно остановить запуск и доложить о необходимости отдельной ротации.

Если нельзя гарантировать отдельную БД, отдельный ключ и loopback-only bind без редактирования исходников — VectorService не запускать. Выполнить только read-only аудит и описать блокер.

## 5. Этап VS-01 — ST-VectorService

### 5.1 Изоляция и запуск

1. Создать новую тестовую копию архива в отдельном временном каталоге, не поверх существующей установки.
2. Использовать отдельный каталог SQLite/Vectra.
3. Выбрать свободный порт, отличный от 8787, например 8791 после проверки доступности.
4. Привязать тестовый экземпляр только к `127.0.0.1`. Если сервис не поддерживает безопасную настройку bind/port через env, не менять исходники — остановиться и отметить BLOCKED.
5. Направить embedding proxy на локальный Ollama либо на отдельный локальный mock endpoint для контролируемых тестов.
6. Запустить тестовый экземпляр и сохранить PID, фактический listen address, порт и путь к тестовой БД.

### 5.2 Health и жизненный цикл

- Успешный `/health` при доступной тестовой БД.
- Некорректная/недоступная тестовая БД: ожидаемый контролируемый отказ, если это можно смоделировать без риска.
- Запуск с отсутствующим обязательным ключом.
- Повторный запуск и повторная инициализация БД.
- Graceful shutdown по штатному сигналу.
- Повторное открытие тестовой БД после завершения: целостность и отсутствие повреждений.
- Таймаут/недоступность embedding backend не должны зависать бесконечно или раскрывать секреты.

### 5.3 Auth

Для каждого защищённого маршрута проверить:

1. Bearer header отсутствует → отказ.
2. Bearer key неверный → отказ.
3. Bearer key корректный → запрос проходит авторизацию и доходит до валидации/обработчика.

Проверить, что ключ не принимается из query string или другого неоговорённого места. Проверить constant-time comparison, если он заявлен в коде; не делать вывод о нём только по наличию функции с похожим названием.

### 5.4 API endpoints

Проверить все защищённые маршруты из фактического роутера:

- `/v1/list`
- `/v1/insert`
- `/v1/delete`
- `/v1/query`
- `/v1/query-multi`
- `/v1/stats`

Для каждого — корректный запрос, пустое/неверное тело, неизвестная коллекция, отсутствующий вектор и ожидаемый HTTP status/error shape.

Функциональный сценарий на отдельной тестовой коллекции:

1. Создать/получить тестовую коллекцию.
2. Вставить несколько небольших тестовых векторов с уникальными тестовыми ID.
3. Проверить list/stats.
4. Выполнить query и query-multi с известными векторами.
5. Проверить topK и threshold на граничных допустимых значениях.
6. Удалить только тестовые ID.
7. Повторно проверить отсутствие удалённых записей.
8. Убедиться, что тестовая БД не содержит данных из рабочей установки.

### 5.5 Валидация и устойчивость

Проверить как минимум:

- отсутствующий/пустой vector;
- нечисловые значения, `NaN`, `Infinity`;
- несовпадающие размерности;
- размерность на границе лимита и выше лимита;
- topK: 0, 1, верхняя граница, выше верхней границы;
- threshold ниже -1, -1, 0, 1, выше 1;
- пустой batch, batch на допустимой границе и выше лимита;
- дублирующиеся ID;
- некорректные имена коллекций/путей;
- большие тела запросов;
- неверные типы полей.

Проверить атомарность: при контролируемой ошибке записи в тестовой БД не должно оставаться частично применённых изменений. Использовать отдельную тестовую копию и fixtures. Не вызывать искусственные ошибки в рабочей БД.

### 5.6 Embedding proxy

Проверить `/api/embed` и `/api/embeddings`:

- без ключа и с неверным ключом — отказ;
- корректный ключ — запрос проходит;
- локальный mock Ollama подтверждает корректный upstream URL, method, body и headers;
- фактический Ollama — отдельный интеграционный тест, только если он уже доступен и нужная модель установлена;
- Ollama недоступен;
- upstream возвращает 4xx/5xx;
- upstream timeout;
- некорректный JSON/ответ;
- отсутствие утечки ключа в логах и ошибках.

Отчётливо разделить:
- proxy unit/integration с mock Ollama;
- реальную интеграцию с Ollama и конкретной embedding-моделью.

Не ставить PASS реальной embedding-интеграции, если проверен только mock.

### 5.7 Логи и сеть

- Проверить stdout/stderr и файлы логов на секреты, Authorization headers, payload и лишние диагностические данные.
- Отдельно оценить диагностические поля token length/hash/match: не публиковать их значения; указать, нужны ли они и не создают ли лишнюю поверхность утечки.
- Подтвердить, что тестовый сервис слушает только loopback.
- Зафиксировать исходящие соединения тестового процесса. Допустимы только локальные адреса тестового Ollama/mock. Любой неожиданный внешний egress — BLOCKED, остановить тестовый процесс и доложить.

### 5.8 Отсутствие штатного test runner

Если `npm test` остаётся заглушкой, зафиксировать это как факт. Не выдавать успешный exit заглушки за тестовый прогон. Использовать внешний временный harness на Node.js built-in `node:test` или другой уже установленный инструмент, не изменяя `package.json` и production source. Приложить команды запуска и результаты.

Проверить:

- Core недоступен;
- connection refused;
- timeout;
- malformed/error response;
- корректное завершение диагностики при ошибке.

Доказать по коду и runtime-наблюдениям, что пакет:

- не читает чаты, сообщения, prompt и историю;
- не отправляет содержимое чатов;
- не читает и не передаёт API tokens/secrets;
- не пишет chat text в логи, SQLite или IndexedDB;
- не вызывает Memory → NPC и не меняет Enrollment;
- не изменяет Core, SQLite или основную ST.

Если диагностический пакет не запускается, не чинить его в этом задании. Сохранить точную ошибку и минимальное воспроизведение.

Не запускать генерацию и не тестировать Swipe/Regenerate/Cancel.

## 10. Критерии завершения

Этап считается завершённым только если:

- VectorService тестировался в изоляции на loopback и отдельной БД либо точный блокер безопасного запуска доказан;
- все доступные API/auth/validation сценарии фактически выполнены;
- mock и real embedding результаты разделены;
- ST→Core диагностика ограничена `/health` и не раскрывает чат/секреты;
- integrity baseline/after сравним;
- каждый непроверенный сценарий честно отмечен;
- нет изменений production-кода, рабочих данных, GitHub workstreams или readiness статусов.

**После VS-01 выдать промежуточный отчёт до продолжения ST-LE-01 и INTEGRITY-01.** Если в ходе VS-01 обнаружится риск для Core, основной ST или рабочих секретов — немедленно остановиться и доложить.
