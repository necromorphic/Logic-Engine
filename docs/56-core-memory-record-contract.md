# Core Memory record contract

Status: proposed. This defines a logical contract, not a committed database schema or public API.

## 1. Record envelope

A durable record should carry the following logical fields. Physical representation may differ if equivalent guarantees are documented.

- `memory_id`: stable opaque identifier, generated by a trusted service; never supplied as authority by a model.
- `world_id`: mandatory isolation boundary. Every source reference must resolve within the same world unless a future explicit cross-world contract says otherwise.
- `record_type`: closed, versioned category such as `source_reference`, `evidence`, `episode`, or `summary`.
- `payload_schema_version`: permits validation and migration without changing the stable record identity.
- `payload`: bounded structured content. Avoid treating arbitrary prose as a canonical fact.
- `epistemic_kind`: typed value such as `canonical_reference`, `observed`, `asserted`, `reported`, `hypothesis`, or `derived_summary`. Values must not be silently upgraded.
- `source_refs[]`: typed references to source records, canonical event/fact IDs, messages, or artifacts; each reference includes its namespace and expected world scope.
- `provenance`: trusted acquisition route/producer identity, source identity, and verification state assigned by the trusted boundary. Caller-declared authorship may be retained as a claim but not as verified provenance.
- `created_at`: service timestamp; distinct from when the represented content occurred.
- `valid_time`: optional event/time interval to which content refers, with explicit timezone/precision where known. Unknown time remains unknown.
- `source_revision` / `source_commit_sequence`: optional Core cursor when content was derived from a canonical snapshot. Never imply these are equivalent to a full causal proof.
- `record_version`: monotonically increasing version for changes to one logical record, or an immutable-version identifier plus a current pointer. Choose one storage strategy before implementation.
- `lifecycle_state`: typed lifecycle state defined in the lifecycle contract.
- `relations[]`: typed links such as `derived_from`, `supersedes`, `disputes`, `supports`, or `references`; links are not truth decisions.
- `audit_ref`: pointer to the memory operation audit record, if audit is stored separately.

## 2. Boundary with Core-owned acquisition, delivery, and belief records

A generic Memory record is not a substitute for the Core-owned semantic records defined by the NPC knowledge proposal. Acquisition history, delivery attempts/status, current belief stance, and canonical proposition truth are distinct concepts. The memory store may be used as a persistence primitive only if Core explicitly assigns that storage path and preserves the required semantics; Memory must not invent parallel acquisition IDs, belief state, delivery ledgers, revision counters, or rollback logic. Search or prompt inclusion never establishes acquisition or delivery.

## 3. Confidence and uncertainty

Do not introduce a generic 0–1 confidence field. Its calibration, comparability, and authority are undefined. Represent uncertainty using explicit epistemic kind, source provenance, verification state, conflict links, and a typed assessment only where a domain contract defines its semantics. A model-generated confidence value is an assertion, not a verified score.

## 3. Identity and versioning

Identity is world-scoped: a `memory_id` from world A must not resolve in world B. Content correction must preserve audit and source lineage. Prefer immutable versions for records whose prior contents may have influenced retrieval or downstream actions; if mutable current rows are used, retain a durable version history with equivalent reconstruction guarantees.

A repeated write is idempotent only when the operation's idempotency key and normalized request match under the declared contract. Reuse with different content must fail with a stable conflict error. Duplicate detection by text similarity is not identity and must not erase distinct provenance.

## 4. Provenance validation

Trusted services set producer identity and acquisition route. The record payload may include `claimed_source`, but it must remain visibly unverified until a trusted adapter/service binds it to an actual source. A digest may verify integrity against a known digest; it cannot independently prove origin or truth.

If provenance is required for a record type and cannot be validated, reject the write or store it only under an explicitly untrusted evidence type that has a stricter read policy. Never silently downgrade a failed trusted write to an accepted trusted record.

## 5. Lifecycle semantics

At minimum, distinguish:
- `active`: available subject to normal authorization and source freshness;
- `stale`: a known source/version changed or an index/source check is pending;
- `disputed`: material conflict remains unresolved;
- `retracted`: record is no longer to be treated as valid support, but the audit trail remains;
- `superseded`: a replacement is linked; old content remains historical;
- `unavailable`: hidden or quarantined from ordinary retrieval;
- `deleted`: logical deletion/tombstone or retention-compliant removal, with physical erasure defined separately.

These are not necessarily one exclusive enum in storage: deletion, visibility, and source freshness may be orthogonal dimensions. Decide the representation based on concrete transition tests. A summary with an invalidated source becomes stale or disputed pending recomputation; it must not remain silently active.

## 6. Errors

The logical contract needs stable error classes for invalid shape/schema, unknown or cross-world references, untrusted provenance, unauthorized write, idempotency conflict, stale source revision, invalid lifecycle transition, source conflict, and storage unavailable. Public error details must not leak the existence or contents of inaccessible records.
