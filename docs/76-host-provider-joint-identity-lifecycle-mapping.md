## 1. Status labels

- **APPROVED SEMANTIC MAPPING** — Core approved the conceptual mapping to an existing draft Provider operation, conditional on the required identity and scope being approved and supplied. This does not approve runtime fields or a production handoff.
- **PROPOSED CONTRACT** — candidate rule needed to make the mapping deterministic; not yet an approved field/schema/API or implemented guarantee.
- **BLOCKED** — current source/contracts cannot prove the required property. Do not implement by guessing or treat fixture callbacks as production authority.

## 3. Minimum contract delta required before cross-block implementation

This is a list of decisions and guarantees, **not** proposed field names or a new API/schema.

1. **Host identity contract (Host + Provider, Core approval):** approve where durable logical-message and per-version IDs live in ST message data, when they are created, how they serialize through save/load/replay, and how the deleted object's exact identity is captured before mutation. Define edit parent lineage, active branch, cancelled/incomplete generation, legacy backfill, and copy/import/restore collision rules.
2. **Trusted scope and source authority (Core-owned):** approve how the Host binds a chat/session to the correct engine world/conversation and how a specific captured version and its ancestry are revalidated as current. Core snapshot markers alone are not source-specific proof.
3. **Complete raw-source inventory/reconciliation (Core + Host, implemented with Provider):** approve the declared inventory domain, authoritative enumeration and consistency boundary, truncation/pagination/concurrent-change detection, complete-empty vs partial/unavailable, and restart/interruption/replay invalidation. Existing Provider canonical-entity reconciliation is not this guarantee.
4. **Retraction and final-use semantics (Core + Provider + Host/disclosure owner):** approve whole-message deletion's complete version set, rollback/revocation invalidation, and the final disclosure-time authorization boundary. Explicitly state non-atomic race limits; no existing local tombstone proves external-store purge or prevents every post-check race.

**Single end-to-end blocker:** no owner-approved, durable Host identity + exact retraction binding tied to a trusted, complete/current source inventory boundary across edit/swipe/delete/chat switch/restart/replay. Until the four decisions above are resolved and the real path is tested, do not add a speculative listener/route/schema or enable production retrieval.
