# User communication and collaboration guide

## Purpose

This project is being built with an owner who is an advanced computer user, but **not a software developer**. Project communication must make the work understandable without requiring the owner to learn software engineering.

The owner has explicitly asked for explanations to be broken down into small, clear steps. This is a project requirement, not a deficiency to be corrected.

## Required communication rules

1. **Start with the practical result.** Explain what a change means for the person using the finished Logic-Engine, before discussing implementation.
2. **Use plain language by default.** Avoid unexplained terms, abbreviations, file names, API names, database details, and test-runner terminology. If a technical term is necessary, explain it immediately in one sentence.
3. **Break explanations down.** Describe one idea at a time. For procedures, give numbered steps and state exactly where to click or what to copy, paste, and expect to see.
4. **Do not assume developer knowledge.** Do not expect the owner to understand Git, branches, commits, pull requests, Node.js, SQL, CI, or test output without explanation.
5. **Do the technical work when authorized tools allow it.** Prefer inspecting the repository, making the change, running checks, and reporting the outcome over asking the owner to perform developer tasks manually.
6. **Ask only for decisions that genuinely belong to the owner.** Explain the choice and its consequences in ordinary language; do not make the owner choose between internal implementation details.
7. **Report status honestly.** Distinguish what works now, what is only a prototype, what has been tested, what remains incomplete, and what is blocked. Never present an estimate as an official completion percentage.
8. **Keep each update manageable.** Lead with a short summary and the single most useful next step. Add technical detail only when needed or requested.
9. **Treat confusion as feedback about the explanation.** If the owner says they do not understand, re-explain more simply and concretely. Do not repeat the same explanation with more jargon.
10. **Do not turn self-deprecating wording into a factual assessment.** The owner may describe herself harshly when overwhelmed; the actionable requirement is to explain things patiently, concretely, and without assuming prior development knowledge.

## Preferred update format

- **What this means:** the real-world effect.
- **What is already working:** only verified facts.
- **What is not working yet:** the remaining gap, in plain language.
- **What happens next:** one concrete action, with the technical work handled by the assistant whenever possible.

## Acceptance criterion

An update is successful when the owner can understand what changed, why it matters, and whether anything is needed from her—without having to understand the underlying code.
