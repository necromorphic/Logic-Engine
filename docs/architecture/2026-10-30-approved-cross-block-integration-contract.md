# Approved cross-block integration contract — 30 October 2026

**Decision authority:** project owner explicitly delegated architectural approval and implementation authority to the coordinator in the project conversation on 30 Oct 2026.
**Status:** APPROVED as the binding private architecture and inter-module contract.
**Production disposition:** Memory → NPC remains `DISABLED / FAIL-CLOSED` until every release gate in §9 is proven.
**Scope:** Core, SillyTavern Host/Adapter, Memory Provider, NPC consumer, Security/Gateway. This decision does not authorize changes to unrelated vectorization semantics or the separate remote vector-store integration.

This decision supersedes any older statement that cross-owner semantic approval is still waiting for a separate owner response. It does not convert draft code, test seams, source inspection, or CI into production proof.

## 1. Authority and ownership — approved

| Boundary | Decision / owner |
|---|---|
| Host session and authenticated account | SillyTavern Host. The server, not browser code, establishes the authenticated session identity. |
| Host conversation identity and lifecycle evidence | Host adapter. It emits persisted logical IDs, version lineage, active/deleted state and content digests; it never claims Core truth. |
| World and actor binding | Core. Core derives world scope from the authenticated adapter + active conversation binding and validates the actor binding. Caller-supplied `world_id`, actor IDs, labels, prompt fields or model output are not authority. |
| Canonical world state, source validity and field visibility | Core. |
| Memory record identity, grants, lineage, index/reconciliation state and exact-version revocation | Memory Provider. |
| NPC admission, epistemic interpretation and uncertainty | NPC. It cannot authorize disclosure, create acquisition, alter canonical truth or own egress. |
| Final model disclosure and outbound transport | PC-side Security Gateway. It is the sole egress authority for every protected request. |
| Accepted-head authority, rollback and secure SQLite open | Security/operations, independently verifiable and fail-closed. |

No component may assume another component's authority from a positive test callback, local metadata, a request label or a successful preflight.

## 2. Two evidence lanes — approved and distinct

### Lane A: Core-owned initial acquisition

`trusted author/import source → Core validation → canonical knowledge.acquire event → Core acquisition projection → Core actor-scoped read + per-acquisition visibility → NPC context`

- Core owns acquisition identity, assignment, validity, rollback and durable belief-transition history.
- Acquisition pins the exact acquired value (or lossless canonical representation) and the sorted canonical source-event set supporting it.
- Legacy/unpinned acquisitions fail closed.
- A Core reader result is not itself a disclosure grant. Per-acquisition visibility must be checked for the exact recipient, actor, purpose, conversation and snapshot before values enter model context.
- This lane does not require Memory Provider retrieval.

### Lane B: Memory Provider evidence

`Provider record → Provider grant/lineage/reconciliation → Core canonical-source and field authorization → NPC admission → NPC cognition`

- The first and only approved Provider consumer source type is `canonical_entity`, with exactly one direct canonical lineage source.
- Provider record identity is `(world_id, record_ref, record_version)`.
- Canonical source identity is `(canonical_entity, source_entity_id, source_version)`.
- For this source type, Provider `source_version` is the canonical decimal string of the exact Core entity's non-negative `updated_revision`. Core must compare exact equality against the current entity in the exact world and reject missing, destroyed, unknown, malformed, mismatched or unavailable state.
- `world_revision + commit_sequence` is a snapshot/staleness marker only. It is not a source-specific change journal.
- Provider record version, canonical source version, Core entity revision and Core snapshot cursor are distinct values; they must never be conflated.
- Summaries, derived copies, raw Host messages, chat swipes and arbitrary Host records are not approved Provider source types.

The two lanes retain their own purposes. Lane A purposes remain `npc_turn_context` / `npc_action_evaluation`; Lane B's current Memory consumer purpose remains `npc_decision`. No implicit purpose alias or mixed context is authorized.

## 3. Host identity and lifecycle envelope — approved semantics

The current Host candidate's opaque conversation identifier format is accepted for the review adapter:

`hostSessionId:installationId:conversationUuid`

with these mandatory interpretations:

1. `hostSessionId` is generated by the SillyTavern server and stored in its signed authenticated session. The session account handle must match the authenticated user handle. It rotates on account/session reset or loss.
2. `conversationUuid` is persisted in the chat metadata and is the logical conversation component.
3. `installationId` is a client-side namespace only. It is not a durable installation attestation, hardware identity, secret, or authority. It may be cloned or restored.
4. The composite is opaque and session-scoped. A changed session must not silently reuse an old Core binding. Existing stale bindings fail closed and require explicit re-binding.
5. File paths, mutable chat array indices, message array indices, swipe indices and display names are never durable identity.
6. The authenticated server route must independently verify the signed session and authenticated account. Browser-supplied session/account/world/actor fields are not trusted.

The Core Host version ledger remains a separate digest-only lifecycle ledger. Its approved bounded reconciliation request semantics are the existing `conversation_id`, `complete`, and `versions[]` contract, with exact `message_id`, `version_id`, `parent_version_id`, `content_sha256`, `active`, and `deleted` fields. Core derives world scope from the authenticated adapter binding; caller-supplied `world_id` and raw message text are rejected. The accepted transport limits are 8 MiB and 25,000 version entries. Oversize inventories are NON_READY; they must not be split into invented cursor/chunk/outbox protocols.

**Critical limitation:** this approves the metadata contract, not a completeness claim. The current Host scan is a bounded double-scanned pathname view, not an atomic filesystem snapshot. It does not recover pre-enrollment or deleted history and does not prove import/export/copy/branch/restore/migration/external-edit coverage, durable installation attestation or rollback resistance. The bridge must continue sending `complete: false`; Core's inventory verifier remains deny-only. No caller can override this with `complete: true` or a positive fixture validator.

## 4. No Host-message-to-Provider identity mapping — explicitly prohibited

The Host tuple `(world_id, conversation_id, message_id, version_id)` belongs to the Host lifecycle ledger.

It must not be mapped to Provider identity `(world_id, record_ref, record_version)`, nor may a Host message or swipe be registered as a `canonical_entity`. The Host ledger's tombstones and active pointers do not revoke or mutate Provider records. Provider exact-version grants/revocation apply only to Provider records.

A future additional Provider source type requires a separate source contract defining authority, identity, version, lineage, lifecycle, inventory completeness, rollback semantics and final disclosure policy. No such type is approved by this decision.

## 5. Reconciliation and revocation — approved ordering

- Provider must recheck exact record/query grants, source lineage/version and readiness after every asynchronous source-validation boundary and immediately before returning an authorized candidate.
- Revocation of one Provider record version must not revoke a sibling version unless the exact grant or scope says so.
- Core must revalidate conversation→world and adapter→actor bindings, source validity and visibility at the final decision boundary.
- A stale, partial, denied, withheld, unavailable, rebuilding or unverifiable inventory is not complete. It produces no protected disclosure.
- A Host capture receipt proves only receipt of that individual digest record. It does not prove complete inventory.
- Host deletion may be inferred only from a trusted complete same-branch inventory after the verifier has established that omission means deletion. The current Host candidate cannot establish this; no deletion inference is currently permitted.
- Core canonical source deletion/retraction remains Core-owned. Provider must not invent a second Core deletion API.

## 6. Final dispatch — approved Security contract

One PC-side Gateway owns both final disclosure authorization and the only outbound transport for each protected request.

The ordering point is the durable `DISPATCH_STARTED` decision. The Gateway must:
1. bind one immutable request ID, route, exact body digest, actor/world/purpose, exact Provider records and source versions;
2. acquire the shared cross-process Coordinator serialization boundary;
3. revalidate Core authority/source state, Provider grants/readiness and accepted-head state;
4. durably commit `DISPATCH_STARTED`;
5. synchronously invoke the actual transport-start callback while still holding the Coordinator lease;
6. release the lease before awaiting the response/stream.

The callback contract is strict: it must initiate the actual network request synchronously before returning its Promise. It may not defer initiation behind an await, timer, queue or callback. A promise is awaited only after the lock is released.

If denial/revocation/readiness loss wins before `DISPATCH_STARTED`, outbound call count is zero. If dispatch-start wins, the request is in flight; later revocation cannot recall bytes already handed to transport. Ambiguous started requests are not automatically retried. Duplicate request IDs are idempotent only for the same exact body and binding; conflicting reuse is rejected.

This contract applies to every enabled backend and every protected generation path, including streaming/non-streaming, regenerate, continuation and retries. The pinned SillyTavern Chat Completions source has multiple provider-specific early-return senders plus a separate OpenAI-compatible fetch path. A route-level hook, prompt-preparation hook, browser event, or generic-fetch-only wrapper is insufficient. All senders must converge on the Gateway transport-start interface, or each sender must be explicitly instrumented and covered by a source inventory guard proving no bypass exists.

## 7. Anti-rollback and secure SQLite open — approved Security requirements

### Accepted-head authority

A client-side Ed25519 verifier is necessary but not sufficient. The authority service must maintain an independently rollback-resistant monotonic sequence/epoch and signed hash chain. The local database, local minimum sequence, a restored backup, or caller-supplied sequence cannot be the sole rollback anchor. Restore/recovery must use a separately authorized epoch/domain transition and must fail closed if the authority is unavailable or history is ambiguous.

### SQLite TOCTOU

Path `stat`/`lstat`/`realpath` checks, BigInt precision, parent ACL assertions or rechecking around `DatabaseSync(path)` do not prove that SQLite opened the object that was checked. The secure boundary must bind validation to the actual OS file handle inside the SQLite open operation and cover Core, Coordinator, Host ledger, Provider and dispatch/accepted-head databases plus WAL/SHM/journal sidecars.

Approved feasibility order:
1. First spike: load a pinned native SQLite VFS extension into the exact same SQLite engine used by Node 22.13+ `node:sqlite`, bootstrapped only from `:memory:`, and prove native default-VFS selection, permanent lifetime, every protected open and sidecar, Windows + POSIX races, and preservation of Session/changeset APIs.
2. If same-engine registration/default selection/lifetime cannot be proved, spike a dedicated native binding that owns SQLite and the VFS while preserving the required Session/changeset behavior.
3. If neither passes the adversarial matrix, protected startup and dispatch remain fail-closed. Repeated path checks are not an acceptable fallback.

This approves the experiment order, not production use of an unproven extension or binding.

## 8. SillyTavern egress and vectorization scope

- Protected Memory bytes must never be sent by direct browser/provider routes. The PC Gateway is the sole protected egress.
- The uploaded Security 1.1 patch's mandatory Google-egress behavior is a separate transport-hardening concern. It may be integrated only after exact pinned-source apply/test review and actual gateway protocol verification.
- Preserve SillyTavern vectorization semantics, existing settings and the separate remote vector-store integration. Do not silently reroute, disable, reconfigure or change vectorization as part of Memory/NPC work.
- Provider keys remain server-side; no gateway password/token in query strings, prompts, client-visible state or logs.
- No raw message text retention is introduced by this contract.

## 9. Release gates — all required, conjunctive

Memory → NPC may be enabled only after all gates pass on one recorded compatible set of Core, Provider, Host and Security SHAs:

1. **Core authority:** production authenticated adapter/session→world and adapter→actor bindings; per-lane source/field/acquisition visibility authorization; all relevant Core writers participate in the shared serialization boundary.
2. **Host identity/inventory:** pinned target attestation; session/account binding; complete active + historical + alternate + deleted inventory; every create/edit/swipe/select/delete/import/export/copy/branch/restore/migration/external mutation covered; atomicity or an equivalent race-proof snapshot; durable rollback/replay detection. No unresolved path may return complete.
3. **Provider:** only approved source identities; trusted source validation from real Core state; durable exact-version grants/revocation; reconciliation and restart/rebuild; no stale snapshot reuse; all Provider writers participate in the shared serialization boundary.
4. **Security dispatch:** every protected sender/path reaches the sole Gateway; zero outbound calls for pre-start denial/revocation/stale inventory; synchronous transport handoff under the shared Coordinator lease; no duplicate on ambiguous start.
5. **Anti-rollback:** independently rollback-resistant accepted-head authority, restore-domain separation and replay protection.
6. **SQLite:** secure-open implementation proven on Windows and POSIX for all protected DBs and sidecars; deterministic race/alias matrix passes.
7. **Operational proof:** actual isolated target SillyTavern runtime tests, exact SHAs, exact CI links, deterministic barriers, observed outbound-call counts, durable state after restart/restore, and no protected content in logs.

A gate cannot be waived by this architecture approval. Any missing, stale, partial, unavailable or ambiguous evidence keeps the system `DISABLED / FAIL-CLOSED`.

## 10. Immediate implementation sequence

1. Land Provider-only regression coverage after exact-head Linux + Windows checks.
2. Reconcile Host session identity and current inventory candidates to this approved opaque identity interpretation; retain NON_READY.
3. Complete Core acquisition-reader/visibility and deployment authorizer composition; do not expose an HTTP or model serializer prematurely.
4. Wire all pinned Host protected sender routes through one PC Gateway transport-start contract.
5. Run the VFS/native secure-open feasibility spike and independently rollback-resistant authority implementation.
6. Only then run the joint Host/Core/Provider reconciliation and revocation race matrix and reconsider enablement.

**Final decision:** the cross-block architecture and semantic contracts above are APPROVED. The present Host, Security, and production dispatch implementations are NOT READY. This approval authorizes implementation of the defined contracts; it does not authorize weakening any release gate or enabling production Memory → NPC.
