# NPC-local Goal and Plan Store — Contract Draft

**Status:** design contract based on the accepted A1 ownership decision in `docs/97-npc-goal-plan-state-ownership-decision.md`.
**Date:** 2026-10-30.
**Implementation status:** not implemented. The first-slice current-plan cardinality rule in §4.3 is accepted. No runtime, API, database schema, migration, dispatcher, scheduler, or automatic execution is authorized by this draft.
**Purpose:** define the smallest durable NPC-domain store contract and its boundary with Core.

## 1. Scope and decision

The store persists only NPC-domain goal/plan continuity needed by the autonomy cycle:

- accepted NPC goals and their NPC-local lifecycle revisions;
- plans belonging to one goal, including ordered steps and plan revisions;
- candidate plan revisions awaiting NPC-domain acceptance;
- the current-plan pointer for each goal;
- append-only NPC-local lifecycle/revision audit;
- bounded references to Core snapshots and authoritative Core results used by planning/reconciliation;
- durable action-attempt/reconciliation checkpoints needed to prevent a Core result from advancing a plan twice.

This is **not** a store for canonical world state. It does not own world facts, entities, events, game time, world revisions, causality, rollback, permissions, Memory acquisition, persistent belief, delivery receipts, or Relationship state.

The decision refines the broad classification in `docs/03-storage-and-persistence-contract.md`: goal/plan/task progress is authoritative within the NPC domain, but it is not a canonical world-state record. Core remains authoritative for whether any world effect occurred.

## 2. Reconciliation with earlier NPC documents

The earlier no-persistence statements remain valid within their original scope:

- `docs/34-npc-decision-context-and-proposal.md` describes the first non-committing decision slice and explicitly excludes durable goals/plans from that slice. This contract is a later, separately approved planning/persistence stage.
- `docs/81-npc-goal-action-contracts-proposal.md` §9's blanket “no persistent NPC store” non-goal is superseded **only for NPC-local goal/plan/task-progress state** by decision A1. Its restrictions on Core, Host, Memory, shared APIs, action dispatch, and world effects remain.
- `docs/89-npc-epistemic-model-stage-1-proposal.md` §2 and §9 remain unchanged: acquisition, provenance, persistent subject-relative belief, delivery/receipt, and source-validity reconciliation remain Core-owned. Do not move them into this store.
- `docs/31-npc-subsystem-contract.md` remains the semantic owner map: goals, plans, tasks, needs, intentions and commitments are NPC-domain state; Core owns canonical effects and causal rollback.

No existing helper is silently upgraded into a persistence API by this document.

## 3. Identity and ownership

### 3.1 Reused Core identities

The store uses existing Core identifiers as references:

- `world_id` identifies the canonical world;
- `npc_entity_id` is the canonical entity ID for the acting NPC, resolved from trusted Core actor binding.

Do not create a second world ID, NPC identity, actor registry, or alias-based identity scheme. A display name, character-card name, model output, or adapter ID is not the NPC identity.

`ActorBindingService` currently binds an authenticated adapter to a canonical entity. That is identity resolution only; it does not grant broad knowledge access or authorize an action.

### 3.2 NPC-local identifiers

The proposed identifier contract is:

- `goal_id`, `plan_id`, `step_id`, `candidate_id`, and `attempt_id` are opaque, immutable identifiers generated by trusted NPC runtime/store code;
- use UUIDv4 generated by the trusted boundary for new records, consistent with the repository's existing `randomUUID()` usage;
- never accept model-generated IDs as proof of ownership or uniqueness;
- scope every lookup and uniqueness check by `(world_id, npc_entity_id)`;
- a plan belongs to exactly one goal; a step belongs to exactly one plan revision lineage;
- changing the semantic identity of a step requires a new `step_id`; editing its display text does not.

The existing pure helpers accept non-empty string IDs and do not enforce UUID format. The persistence adapter must validate the proposed ID contract; changing helper schemas is a separate implementation task.

## 4. Domain records and revision semantics

### 4.1 Goal

A goal record contains at least:

- `world_id`, `npc_entity_id`, `goal_id`;
- goal description/desired-condition payload;
- origin/provenance references supplied by an approved source;
- lifecycle status and transition reason;
- `goal_revision`, starting at 1 and increasing on each accepted goal-domain mutation;
- creation/update timestamps for diagnostics only.

The existing `transitionNpcGoal` helper accepts `active | blocked | completed | abandoned`; completed and abandoned are terminal. The helper validates a proposed transition but does not authenticate the event that motivated it.

The store persists only goals that have already passed an explicitly owned admissibility/acceptance policy. Goal generation and goal admissibility remain separate blockers; this contract does not invent their policy or make model-proposed goals active automatically.

### 4.2 Plan and plan revisions

A plan belongs to exactly one `goal_id`. A plan record contains:

- `world_id`, `npc_entity_id`, `goal_id`, `plan_id`;
- monotonically increasing `plan_revision` within that logical plan;
- ordered step payload, including stable `step_id`, `action_id`, and progress status;
- assumptions, prerequisites, blockers, alternatives and bounded provenance references;
- Core snapshot basis `(world_revision, commit_sequence)`, when supplied;
- plan execution status, distinct from selection/supersession status.

The existing `advanceNpcPlan` helper accepts plan status `active | blocked | completed | abandoned`; step status `pending | active | blocked | completed`. It requires exactly one active step for an active plan and does not authenticate caller-reported outcomes.

**Supersession is not a plan execution status.** Keep the helper's existing lifecycle vocabulary separate from store selection metadata such as `candidate`, `current`, `superseded`, or `rejected`. Do not add `superseded` to the helper's status enum merely to represent that another plan was selected.

### 4.3 Current plan and alternatives

Accepted bounded first-slice rule:

- a goal may retain multiple plan candidates/alternatives;
- at most one plan is selected as the current plan for a goal at a time;
- the current-plan pointer is stored separately from goal lifecycle status;
- accepting a replacement marks the previous current plan as superseded in store metadata and selects the accepted plan;
- the previous plan and its revisions remain in history; they are not deleted;
- a completed/abandoned plan is not automatically replaced, and a failed plan does not automatically complete or abandon its goal.

This rule matches the current autonomy-cycle helper, which evaluates one supplied current plan per pass, while preserving alternatives as candidates. It is an accepted first-slice architecture constraint; the runtime does not yet enforce it.

### 4.4 Distinct version dimensions

Do not collapse these values:

| Version | Owner | Changes when |
|---|---|---|
| `goal_revision` | NPC store | Goal content or goal lifecycle changes |
| `plan_revision` | NPC store | A new accepted revision of that logical plan is recorded |
| `plan_selection_revision` | NPC store | The selected current-plan pointer for a goal changes |
| `store_schema_version` | NPC store | Persistence format migration; not freshness |
| `world_revision` | Core | Canonical world mutation or rollback/correction |
| `commit_sequence` | Core | Canonical commit sequence advances; it must be paired with world revision for snapshot identity |

A Core snapshot cursor is evidence of the world view used to assess a plan. It is not an NPC plan version. A plan revision is not evidence that its world assumptions remain true. Do not use `commit_sequence` alone to establish currentness or invalidation.

## 5. Candidate creation and atomic acceptance

A generated/revised plan is a candidate until accepted by the NPC-domain owner.

Candidate metadata must bind:

- exact `world_id`, `npc_entity_id`, `goal_id`;
- candidate ID and proposed plan identity/revision;
- expected `goal_revision`;
- expected `plan_selection_revision`;
- expected current `plan_id` and `plan_revision`, including explicit null when no plan is current;
- the snapshot basis and evidence references used to produce the candidate;
- a bounded reason for creating/revising/replacing the plan.

Candidate creation does not mutate the current goal, current plan, plan progress, or canonical world.

Acceptance is one atomic NPC-store transaction:

1. validate the acting NPC scope and exact goal/candidate linkage;
2. compare the expected goal revision and plan-selection revision;
3. compare the expected current plan identity/revision;
4. validate the candidate's structure and allowed transition;
5. persist the accepted plan revision;
6. mark the previous current plan superseded, if one exists;
7. move the current-plan pointer and increment `plan_selection_revision`;
8. append one NPC-local audit entry.

Any mismatch returns a stale/conflict/review result with no partial writes. Do not silently rebase, overwrite a newer plan, or accept a candidate for a different goal.

Plan acceptance is an NPC-domain state transition only. It does not create a Core event, advance game time, authorize an action, or prove that the plan's world assumptions are still current.

## 6. Repository boundary and atomicity

Cognition helpers must receive plain domain values and return pure results. They must not receive a database connection, execute SQL, or know the physical storage technology.

A future NPC-owned repository boundary should expose only bounded operations equivalent to:

- load one NPC's goal/plan decision state;
- create a candidate without changing current state;
- accept/reject a candidate using expected-version compare-and-swap;
- apply an authenticated goal transition;
- reconcile one verified Core result idempotently;
- list bounded pending reconciliation work;
- read the NPC-local revision/audit history needed for diagnosis.

These are conceptual operations, not a public API. The proposed internal operation semantics, failure classes, atomicity requirements, and test contract are specified in `docs/99-npc-goal-plan-repository-interface-contract.md`; implementation remains blocked by the gates listed there.

A store mutation must atomically persist the domain record change, current-plan pointer update (where relevant), local audit entry, and local idempotency outcome. The storage engine/file layout is intentionally not selected here. `docs/03` says the production storage and physical-isolation strategy remain open; A1 requires logical and physical separation from Core's canonical SQLite store, but does not require SQLite for the NPC store.

The repository adapter is the only component allowed to access the NPC store. No direct Core SQLite access is permitted from NPC cognition or the NPC repository.

## 7. Core context and world-effect boundary

The intended data flow is:

    NPC repository -> NPC cognition
         |                |
         |                | bounded read request
         |                v
         |          Core AuthorizedReadService
         |                |
         |                v
         |          actor-/purpose-filtered snapshot
         |                |
         |          NPC evaluates/revises plan
         |                |
         |                v
         |          action proposal
         |                |
         |                v
         |          Core proposal -> approval -> commit
         |                |
         |                v
         +<---- verified Core result / reconciliation

Rules:

- Core remains the source of current canonical world facts and authoritative world revision.
- NPC-local goal/plan assumptions are not copied into Core as canonical facts.
- The NPC must obtain current world context through an approved actor-bound, purpose-bound, field-filtered Core read. Raw `getSnapshot` data and context-manifest membership are not model-safe authorization.
- `AuthorizedReadService` currently rechecks actor binding and the composite snapshot cursor after policy evaluation. Its default policy remains narrow/self-only; arbitrary NPC-to-world reads require an explicitly trusted field policy.
- `ActorBindingService` binds adapter identity to an NPC entity but does not authorize action semantics.
- A plan step is not executable merely because it is current. Every world-affecting action requires the existing Core validation, proposal, approval, and commit lifecycle.
- Current `ProposalService` uses adapter identity, not an NPC-specific actor authorization contract. Generic proposal validation explicitly does not prove actor authorization, semantic alignment, causal completeness, or player-agency policy.
- Every event currently requires a separate approval step. This contract does not authorize automatic approval or automatic commit.
- Unsupported action/effect mappings remain unsupported; do not smuggle goals, tasks, movement, or relationship changes through generic attributes or `fact.set`.

## 8. Cross-store action attempt and result reconciliation

The NPC store and Core store are separate. They cannot share one SQLite transaction or claim atomic commit across both stores. Use a durable, idempotent handoff:

1. Before submitting an action proposal, persist an NPC-local action-attempt record containing `attempt_id`, NPC/goal/plan/step identities and revisions, the Core snapshot pair, and a stable request hash/idempotency key.
2. Submit through the existing Core proposal path using the same idempotency identity on retries. Same key + same request must resolve to the same proposal; same key + different content must fail as a conflict.
3. Keep pending/approved/committed as Core proposal states. NPC-local attempt state must not impersonate those statuses.
4. Only after Core returns a committed result with a verifiable `event_id` and resulting world cursor may the NPC store reconcile the step.
5. Reconciliation is one NPC-store transaction that records the Core result reference and applies the corresponding pure plan-progress reducer result.
6. A unique constraint/idempotency record over the authoritative Core result identity prevents the same event from advancing the same plan step twice.
7. If the process stops after Core commit but before local reconciliation, recovery must retrieve/replay the same Core proposal result through an authorized Core path and complete the same local reconciliation. It must not create a new action attempt or repeat the world effect.
8. If the exact Core result cannot be recovered or correlated, keep the attempt unresolved/needs-review. Never infer success from model output, intention, dispatch attempt, proposal creation, approval, or an unverified caller flag.

The existing `ProposalService` provides a useful partial primitive: proposal creation is idempotent by `(world_id, idempotency_key, request_hash)`; approval and commit recheck the composite world snapshot; committing an already committed proposal returns its stored commit result as an idempotent replay. This is not yet an NPC-specific dispatcher or proof that the current adapter can safely recover every interrupted attempt.

## 9. Restart, recovery, and rollback

### Restart

After restart:

- load the NPC-local goal/plan state and pending attempts;
- do not assume the stored world snapshot is current;
- reacquire the required context through Core before allowing another action;
- recover pending attempts by their original idempotency/proposal identity;
- reconcile only verifiable Core results;
- do not replay a world effect because the local store missed the reconciliation write.

If the NPC store is missing, corrupt, unavailable, or cannot establish record integrity/version, the affected NPC planning path becomes non-ready/needs-review. Do not silently create an empty goal set or reset plan progress.

### Core rollback

Core remains the only owner of canonical rollback and invalidation.

NPC-local records may retain references to Core event IDs that supported a completed step or plan assumption. When Core invalidates a referenced event:

- reassess only dependent NPC-local progress;
- preserve independently supported progress;
- do not create a parallel rollback engine or world-event log;
- do not infer independence from chronology;
- if causal dependency or current event validity cannot be established, mark the affected plan/attempt needs-review.

The current source audit does not establish a production Core-to-NPC invalidation feed or reconciliation caller. Automatic rollback reconciliation therefore remains blocked until that exact handoff is specified and tested.

## 10. Security and fail-closed rules

- Store access is scoped to the authenticated runtime and exact `(world_id, npc_entity_id)`.
- The model never receives store credentials, SQL access, or authority to choose another NPC's storage scope.
- Model-generated IDs, versions, statuses, success claims, event references and provenance are untrusted.
- The trusted adapter resolves the canonical NPC identity; a character name or card identifier is not sufficient.
- Missing actor binding, missing field policy, withheld/incomplete context, stale snapshot, ambiguous goal-plan linkage, stale expected revisions, or unverifiable Core result must fail closed.
- The NPC store is not an authorization source for canonical actions and cannot grant access to Core state.

## 11. Acceptance tests required before implementation

### NPC-store tests

1. Cross-world and cross-NPC reads/writes are isolated.
2. Goal and plan IDs are immutable and scoped to the correct NPC/world.
3. A plan cannot be attached to two goals.
4. Candidate creation leaves current goal/plan state unchanged.
5. Two concurrent candidate acceptances using the same expected revisions cannot both win.
6. A stale goal revision or current-plan pointer rejects acceptance with no partial writes.
7. Accepting a replacement atomically updates the current pointer, supersession metadata, and audit entry.
8. Replaying the same local acceptance is idempotent; reusing its key with different content conflicts.
9. Corrupt/missing store state fails closed and does not reset progress.

### Core integration and recovery tests

10. Adapter-to-NPC identity is trusted; a caller cannot substitute another NPC.
11. Authorized reads use the exact `(world_revision, commit_sequence)` pair and deny by default when the field policy does not explicitly allow a field.
12. A plan step cannot be marked successful from a pending or approved proposal.
13. A committed Core result advances one step exactly once, including duplicate delivery.
14. Crash after Core commit but before NPC reconciliation recovers the same result without a second world effect.
15. A stale Core snapshot is rejected by the existing proposal/approval/commit checks.
16. Core rollback of the only supporting event makes dependent progress review-required; independent progress survives.
17. Missing invalidation/result linkage remains needs-review rather than guessed.

The tests must exercise the real repository and Core service boundaries. Mocks may isolate pure helpers but cannot stand in for authorization, proposal, commit, recovery, or rollback evidence.

## 12. Implementation blockers and sequencing

The following are not solved by adding the NPC store:

1. Goal admissibility owner and first supported goal family remain unconfirmed.
2. The trusted NPC decision-context builder and complete actor/purpose/field policy are not established. The shipped authorized-read default is self-only.
3. Adapter identity is not the same as NPC actor authorization.
4. The existing generic proposal path still requires separate approval and does not prove NPC semantic/player-agency authorization.
5. No production NPC action-candidate discovery/dispatcher is verified.
6. No Core-to-NPC event invalidation/reconciliation handoff is verified.
7. The physical NPC-store engine, path, backup/restore and migration strategy remain unselected.

Therefore the next implementation should be split: first implement/test the NPC-local repository and atomic lifecycle operations against the accepted domain contract; do not wire autonomous world actions until the independent Core/Host trust and dispatch gates pass.
